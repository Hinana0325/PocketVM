# F1: Is booting Windows 11 ARM64 on QEMU's stock `-machine virt` possible at all, and is an early-kernel halt of exactly this shape (Data Abort writing an unmapped address, then `b .`) a documented or commonly-reported failure mode? Establish the general feasibility picture and any known failure modes specific to the standard virt machine.

## Findings

### [1] Windows 11 ARM64 does boot on stock `-machine virt` and reaches the desktop — but every verified success uses hardware acceleration (KVM/HVF/WHPX), not TCG.
- quote: "Guest: Windows 11 IoT LTSC ARM64 ... The resulting QEMU configuration for the tested Windows ARM64 guest includes: `-machine virt,highmem=on,accel=kvm` ... The guest boots successfully and reaches the Windows desktop."
- url: https://github.com/quickemu-project/quickemu/pull/1942 (PR body retrieved via the GitHub REST search API at api.github.com)
- source_type: community
- published: 2026-08-08
- confidence: high

### [2] That same quickemu PR documents the concrete per-device deltas Windows ARM64 needs on `virt`, all of which are device/firmware-level rather than CPU-independent: no HPET machine property, no x86 CPU flags, `virtio-gpu-pci` instead of `qxl-vga`, and the monolithic EDK2 firmware `QEMU_EFI.fd`.
- quote: "avoid applying the HPET machine property to ARM64 Windows guests ... use **virtio-gpu-pci** instead of **qxl-vga** for Windows ARM64 guests ... prefer monolithic EDK2 firmware (**QEMU_EFI.fd**) for Windows ARM64 guests when available"
- url: https://github.com/quickemu-project/quickemu/pull/1942 (PR body retrieved via the GitHub REST search API at api.github.com)
- source_type: community
- published: 2026-08-08
- confidence: high

### [3] UTM — a shipping product whose QEMU backend is exactly `qemu-system-aarch64 -machine virt` — documents Windows 11 ARM64 installation as a supported first-class flow on that machine, requiring TPM 2.0 + Secure Boot and at least 2 vCPUs.
- quote: "Windows require at least 2 cores to install."
- url: https://docs.getutm.app/guides/windows/
- source_type: primary
- published: unknown (current docs as of 2026-10-23)
- confidence: high

### [4] UTM's own troubleshooting section records two documented, Windows-version-specific failures on this stack — a BSOD for any build below 21390, and a Windows 11 24H2 graphics-driver incompatibility that stalls the installer at a black screen — establishing that "installer starts then the guest stops" has multiple known, Windows-build-dependent causes on `virt`.
- quote: "Installer crashes with BSOD `SYSTEM_THREAD_EXCEPTION_NOT_HANDLED` ... The build number should be 21390 or higher." / "Windows 11 24H2 has a compatibility issue with the graphics drivers that are provided by the UTM guest tools ISO."
- url: https://docs.getutm.app/guides/windows/
- source_type: primary
- published: unknown (current docs as of 2026-10-23)
- confidence: high

### [5] The closest commonly-reported analogue of PocketVM's halt is a silent early-boot freeze immediately after the firmware hands control to the Windows bootloader, with the vCPU(s) spinning at full load and zero guest output — and it is explicitly NOT specific to the accelerator: it reproduces identically under `-accel hvf` and `-accel tcg`.
- quote: "The firmware (EDK2) successfully finds and loads the boot entry, then freezes solid the instant it tries to execute it. CPU usage stays pegged at ~270-290% (multi-core) indefinitely with zero further guest activity" / isolation table row: "CPU acceleration | `-accel hvf` (hardware) vs. `-accel tcg` (pure software emulation) | Hangs identically — rules out HVF/Hypervisor.framework specifically"
- url: https://github.com/utmapp/UTM/issues/7850
- source_type: community
- published: 2026-09-03
- confidence: high

### [6] In the same report the halt is invariant across every device axis the reporter could vary (usb-storage CD vs virtio-scsi `scsi-cd` vs plain `virtio-blk`, `virtio-gpu-gl-pci` vs `virtio-gpu-pci`, TPM on/off, Secure Boot firmware vs non-secure), which matches PocketVM's observation that its own halt is unchanged by CPU model, `pauth`, `-smp` and edk2 build — i.e. the failure is not parameter-tunable on either setup.
- quote: "I methodically varied every VM-configuration axis I could think of; all combinations produce the identical hang at the same point ("starting BootXXXX", zero output after)"
- url: https://github.com/utmapp/UTM/issues/7850
- source_type: community
- published: 2026-09-03
- confidence: high

### [7] The Windows *media build* is a live variable in this failure class: a UTM contributor states the failing ISO is too old and that fresh 25H2/26H1 media boot fine on the identical UTM/QEMU build, while a second user reports the same hang with the *newest* CrystalFetch-obtained media — so newer media is a cheap experiment but not a guaranteed fix.
- quote: "This is an actual problem, but this ISO is really old and ARM64 Windows changes a lot. I have fresh 25H2 and 26H1 media, both work fine on 5.0.5" / "I have the exact same issue right now whenever I try to setup a fresh machine with the newest media obtained from CrystalFetch on an M5 Air running Golden Gate"
- url: https://github.com/utmapp/UTM/issues/7850
- source_type: community
- published: 2026-09-03 (contributor comment) / 2026-09-09 (second reporter)
- confidence: high

### [8] The same spin-class failure is reported specifically from an Android phone running QEMU with `-machine virt` and a Windows 11 Arm64 ISO (host: Redmi Note 11T Pro+, MT6895, Android 15, KVM present), showing the failure is reproducible on the same host class as PocketVM and that switching the firmware container (`-bios` vs a 64 MiB pflash code+vars pair) does not clear it.
- quote: "`-bios` vs pflash: this looked like the cause ... but replacing `-bios` with a standard 64 MiB pflash0 (code) + 64 MiB pflash1 (vars) pair gives the *same* 5 bytes of garbage and the same spin" / "exactly one vCPU is spinning in a tight loop and the rest are idle"
- url: https://github.com/Droid-VM/DroidVM/issues/78 (issue body retrieved via the GitHub REST search API at api.github.com)
- source_type: community
- published: 2026-10-05
- confidence: medium

### [9] No source found documents PocketVM's exact signature — a Data Abort taken in the guest followed by an exception handler executing `b .` taken from a firmware/Windows image. Every third-party report in this failure class describes the *symptom* (freeze + CPU spin, no console output, no guest-side exception dump), never an ESR/FAR/ELR. Treat PocketVM's ESR 0x25/0x96000047 + FAR=0x0 + `b .` trace as unique instrumentation rather than a recognised, searchable failure signature.
- quote: "The VNC console shows **"display output is not active"**, and the guest vCPU burns 100 % of a core forever. Serial shows only 5 bytes of garbage." (the DroidVM record stops at symptom level too)
- url: https://api.github.com/search/issues?q=qemu+windows+arm64+%22machine+virt%22&per_page=10 ; https://github.com/utmapp/UTM/issues/7850 ; https://github.com/Droid-VM/DroidVM/issues/78
- source_type: community
- published: n/a (negative result across 2026-09-03, 2026-10-05 reports)
- confidence: medium

### [10] ESR 0x96000047 is a standard ARM64 encoding — EC 0x25 (Data Abort, current EL) with ISS 0x47 meaning WnR=1 (write) and DFSC 0b000111 (level 3 translation fault) — and independent real-world occurrences of exactly this ESR were root-caused to a *guest software* page-table bug (a missing ISB/TLBI after page-table maintenance), not to an emulator device defect, which is the pattern PocketVM's FAR=0x0 write fault at a non-zero ELR also fits.
- quote: "`ESR = 0x96000047` ... `EC = 0x25: DABT (current EL)` ... `ISV = 0, ISS = 0x00000047, CM = 0, WnR = 1`" and separately "`do_bsys_alloc()` calls `map_phys()` to configure the page tables and then `memset()` to clear it, but there's no `isb` in between." (ESR `96000047`, FAR `ffff80000000a000`)
- url: https://github.com/AmpereComputing/ampere-lts-kernel---DEPRECATED/issues/32 and https://github.com/richlowe/illumos-gate/pull/205 (both retrieved via the GitHub REST search API at api.github.com)
- source_type: community
- published: 2021-05-12 (Ampere) / 2025-10-17 (illumos-gate)
- confidence: medium

### [11] TPM absence/brokenness is a second documented Windows-on-`virt` blocker: with QEMU 10.0.2 on the `virt` machine, `tpm-tis-device` lacks the newer ARM-virt `ppi` option and Windows shows the TPM as present but failed to start, which is directly relevant to PocketVM's `Tpm2SubmitCommand - Tcg2 - Not Found` state.
- quote: "The TPM shows up but doesn't start. Device Manager has 'Trusted Platform Module 2.0' (ACPI\MSFT0101\0) with Problem Code 10 (CM_PROB_FAILED_START), status 0xC0000186. ... The bundled QEMU 10.0.2 doesn't have the 'ppi' option on that device that newer QEMU docs mention for ARM virt." (the same reporter notes UTM uses `tpm-crb-device` with `-machine virt` and Windows sees the CPU as "virt-10.0", with 'virt-8.0' rejected by PC Health Check)
- url: https://github.com/allisonfm85/accessible-virtual-machine/issues/17 (issue body retrieved via the GitHub REST search API at api.github.com)
- source_type: community
- published: 2026-10-09
- confidence: medium

### [12] Net feasibility picture for PocketVM: every source that reaches a Windows 11 ARM64 desktop or Setup screen on stock `-machine virt` uses KVM, HVF or WHPX acceleration (quickemu on Asahi/M1 KVM; UTM docs and issue reports on HVF), and no source found reports a completed Windows 11 ARM64 install on stock `virt` under pure TCG — while the UTM report proves that when the guest does halt early, switching between accelerated and TCG emulation changes nothing, so PocketVM's TCG-only constraint cannot be blamed for the halt itself but also has no precedent of getting past it.
- quote: "CPU acceleration | `-accel hvf` (hardware) vs. `-accel tcg` (pure software emulation) | Hangs identically — rules out HVF/Hypervisor.framework specifically"
- url: https://github.com/utmapp/UTM/issues/7850 ; https://docs.getutm.app/guides/windows/ ; https://github.com/quickemu-project/quickemu/pull/1942
- source_type: community
- published: 2026-09-03 / 2026-08-08
- confidence: medium

- GitHub issue search for `96000047` (16 hits) surfaced only unrelated ARM64 kernel oopses (Ampere/openEuler TPM probe, ODROID USB lockup, CROSSCON hypervisor) — no Windows guest, no QEMU.
- GitHub issue search for `"machine virt" windows arm64 "TCG"` and for ACPI/patched-virt wording returned ~98 and 8 hits but nothing upstream or Windows-specific (self-authored QEMU forks' roadmaps, VirtualBox nested-KVM work, unrelated repos).
- UTM's `guest-support/windows/` page was fetched and yielded only driver/SPICE-tools content — no boot-failure or TCG-vs-HVF guidance.

## Suggested follow-ups
- Search specifically for any Windows 11 ARM64 install that completes under **`-accel tcg`** on stock `virt` (UTM "Emulate" mode / iOS users, Termux-on-Android QEMU users, TCG-only Linux hosts) — this is the one claim with zero positive evidence found here and it decides PocketVM's path.
- Run the cheap decisive experiment PocketVM's bit-for-bit x86_64 reproduction enables: same QEMU 11.1.0 + same argv, but swap the ISO between the failing 26100-era media and a 25H2/26H1 image, and check whether the Data Abort at FAR=0x0 disappears (UTM's parallel report says media build changes the outcome).
- Check the Windows-side platform contract (Microsoft's own ARM64 VM/firmware requirements: TPM `ppi`/`MSFT0101`, ACPI/GTDT, AHCI-vs-virtio storage, secure boot) to see whether the missing pieces PocketVM has already hit (no TPM, no AHCI in ARMVirtQemu firmware, no vioscsi in WinPE) are documented requirements rather than just field observations.
