# F5: First-hand practitioner reports of running Windows 11 ARM64 under QEMU — successes, configurations, and reported early halts.

## Findings

### [1] iPXE's maintainer reports that Windows-on-ARM assumes EL3/ATF is present and can answer `smc`; there is none on QEMU's `virt` machine, and because KVM wrongly emulates `smc` as a no-op the VM happens to boot, while under TCG `smc` is emulated correctly and crashes the VM.
- quote: "Windows on ARM assumes that EL3 is supported and that ATF (or some other Secure World firmware) is present and able to respond to `smc` instructions, but this isn't the case on the QEMU `virt` machine type. If you're using ARM KVM then the `smc` instruction gets emulated incorrectly as a no-op, and this bug causes the system to actually boot correctly. If you're using TCG (e.g. running `qemu-system-aarch64` on an x86 box), then the `smc` instruction gets emulated correctly and crashes the VM."
- url: https://github.com/ipxe/wimboot/issues/4
- source_type: community
- published: 2026-03-18
- confidence: high

### [2] The only configuration that maintainer ever got Windows booting under QEMU was EDK2's `SbsaQemu` firmware built from source on the `sbsa-ref` machine, running Windows 10 (explicitly not 11).
- quote: "The only combination I've found so that that works is to build EDK2's `SbsaQemu` firmware from source and use it in a `sbsa-ref` QEMU virtual machine to boot an MSDN-downloaded Windows 10 (not 11) image."
- url: https://github.com/ipxe/wimboot/issues/4
- source_type: community
- published: 2024-02-08
- confidence: high

### [3] As of March 2026 the maintainer's assessment is unchanged and still unfixed upstream: Windows on ARM cannot run in QEMU on Fedora without patching and rebuilding QEMU, because his attempt to get `sbsa-ref` plus ATF into Fedora was abandoned after a rejected package change.
- quote: "So two years later, it's still the situation that you can't get Windows on ARM running in QEMU on Fedora unless you patch and rebuild QEMU."
- url: https://github.com/ipxe/wimboot/issues/4
- source_type: community
- published: 2026-03-18
- confidence: high

### [4] The same maintainer states Windows requires a Secure World reachable over HVC, which "is not supported in most configurations of QEMU" — and he calls the whole ARM Windows ecosystem "extremely immature" because OEMs ship heavily customised boot-critical images.
- quote: "Windows requires the hypervisor and firmware to support a Secure World accessed via HVC, but this is not supported in most configurations of QEMU."
- url: https://github.com/ipxe/wimboot/issues/4
- source_type: community
- published: 2024-04-08
- confidence: medium

### [5] A first-hand report to QEMU's own tracker confirms Windows 11 Pro ARM64 build 26200.9550 (25H2) actually running on `-machine virt` with QEMU 11.1.2, edk2-aarch64-code.fd and `-cpu host` accel=hvf — and notes the identical command line with `accel=tcg -cpu cortex-a72` also boots.
- quote: "The same command with `accel=tcg -cpu cortex-a72` boots; without the TPM device, HVF boots; with `ppi=off` HVF boots."
- url: https://gitlab.com/qemu-project/qemu/-/work_items/4663
- source_type: primary
- published: 2026-10-08
- confidence: high

### [6] The canonical maintained install guide (referenced as the successor by the `waq` project, and the reference most practitioners follow) was updated in Dec 2024 to use Microsoft's official Windows 11 ARM64 ISO, and explicitly gives a TCG recipe for hosts without aarch64 virtualization.
- quote: "When following this guide on a host not capable of aarch64 virtualization, replace `-cpu host -accel kvm` with `-cpu neoverse-n1` (faster to emulate then `-cpu max`)."
- url: https://gist.github.com/Vogtinator/293c4f90c5e92838f7e72610725905fd
- source_type: community
- published: 2024-12 (latest revision; gist predates it)
- confidence: high

### [7] That guide's tested configuration is `-M virt` with `-cpu host -accel kvm`, `-device ramfb` + `-device virtio-gpu-pci`, `qemu-xhci` with `usb-kbd`/`usb-tablet`, the ISO and virtio-win both as `usb-storage`, a `virtio-blk` disk, plus a `-nic user,model=virtio-net-pci` (network became mandatory to finish setup), and it still requires the `LabConfig` TPM/SecureBoot bypass in the guest.
- quote: "At least since build 25931, it's necessary to provide a network connection to finish the initial setup."
- url: https://gist.github.com/Vogtinator/293c4f90c5e92838f7e72610725905fd
- source_type: community
- published: 2024-12 (latest revision; gist predates it)
- confidence: high

### [8] A complete, current, tested end-to-end Windows 11 Pro ARM install exists on QEMU 10.0.8 with KVM on a Raspberry Pi 5, and its documented configuration confirms several prerequisites the `virt` machine does not give for free — notably that virtio-snd has no Windows driver and USB audio must be used instead.
- quote: "This guide documents a working setup tested on Pi 5 16 GB with a 128 GB SD card, QEMU 10.0.8, and a slipstreamed Windows 11 ARM ISO built with UUPdump."
- url: https://github.com/chronic8000/win11-pi5-kiosk
- source_type: community
- published: unknown (repo created 2026; 3 commits)
- confidence: high

### [9] A Windows 11 ARM64 install under QEMU/KVM succeeds in October 2026 but only after manually feeding the guest drivers twice: `vioscsi` before Setup can read the installer ISO, and `NetKVM` before OOBE will proceed — and WinPE text-field typing drops characters in this environment.
- quote: "Windows 11 ARM64 installs and first-boots under QEMU/KVM, but only after manual driver steps"
- url: https://github.com/techmore/ElementaryOS_MSeries/issues/265
- source_type: community
- published: 2026-10-19
- confidence: high

### [10] A practitioner running QEMU TCG on an x86_64 host reports Windows 11 24H2 arm64 WinPE (build 26100) failing to boot outright, initially attributed to the CPU model (`cortex-a76` fails, `cortex-a710` works) and then re-diagnosed as an intermittent fault that disappeared when the `virtualization=true` CPU property was removed.
- quote: "the 26100 arm64 winpe doesn't boot under qemu tcg cpu cortex-a76, but does under cortex-a710"
- url: https://github.com/jeremyd2019/winautoconfig/issues/5
- source_type: community
- published: 2024-11-14 (re-diagnosis 2024-12-06)
- confidence: high

### [11] The `waq` project's working recipe (Windows 10 17134 ARM64, TCG, `-M virt -cpu cortex-a72 -smp 3 --accel tcg,thread=multi -m 2048`, disk as `usb-storage`) does boot and install, but its own author now calls the project outdated and redirects to the Vogtinator gist; a user attempting the same thing on KVM got only a black screen.
- quote: "Btw, this project is outdated (as written in readme), so it's better to find a new solution to run WoA (like the one in the readme link)."
- url: https://github.com/raspiduino/waq/issues/8
- source_type: community
- published: 2022-09-15 (owner's redirect note 2024-11-26)
- confidence: medium

### [12] An ARM64 WinPE boot under QEMU/OVMF via iPXE+wimboot reaches exactly the point PocketVM reaches — `Loading files...` — and then produces no GUI at all, with the VNC console reporting no display; the thread was never resolved.
- quote: "The final message is `Forcing text mode output` then `Loading files...`. However, the gui screen of winpe didn't show up and `VNC console` just show \"Guest disabled display\""
- url: https://github.com/ipxe/wimboot/issues/4
- source_type: community
- published: 2024-04-08
- confidence: high

### [13] The same failure class is reported on real ARM64 hardware as intermittent and Secure-Boot-dependent (~50/50), and the reporter says he previously reproduced it "using a QEMU command line to test booting an aarch64 vm on an x64 host" — an unresolved thread as of Oct 2026.
- quote: "Ran into this on a Microsoft Surface Laptop (7th Edition) with ARM64, it appears to only happen intermittently when Secure Boot is enabled."
- url: https://github.com/ipxe/wimboot/issues/4
- source_type: community
- published: 2026-10-13
- confidence: medium

### [14] Adjacent, non-QEMU evidence that the ARM64 Windows problem is solvable by not using QEMU at all: a full unattended Windows 11 ARM64 install is verified end-to-end on Apple's Virtualization.framework (macOS, M4 Pro), where the key blockers were firmware/PMU emulation and the fact that Windows creates its own firmware boot entry from the second boot onward.
- quote: "On Apple silicon (Windows 11 ARM) it is verified end to end: the built VM reaches a working desktop with display, network, shared folders, virtio-vsock and the cakeagent service reachable from the host."
- url: https://github.com/Fred78290/caker/pull/147
- source_type: community
- published: 2026-10-17
- confidence: medium

## Dead ends

- No public report anywhere contains PocketVM's exact signature (ESR `0x25/0x96000047`, FAR `0x0`, `b .` self-loop `0x14000000` at `0x…637200`). Searched QEMU's GitLab issue tracker by API (`search=windows`, `search=winpe`) and GitHub's issue-search API; nothing matched this shape.
- QEMU GitLab issue search for `winpe` returned only x86/SeaBIOS issues (#2739 wimboot/newc feature, #1115 SeaBIOS MBR stall, #774 q35-6.1 NIC) — no ARM WinPE halt report exists upstream.
- The configured search engine (`cn.bing.com`, from `edition-defaults.json`) returned the identical set of generic QEMU homepages for every query, ignoring all query terms, including with `&ensearch=1` — unusable for this angle.
- Blocked by transport errors from this network, so never read: `html.duckduckgo.com`, `lite.duckduckgo.com`, `mojeek.com`, `search.brave.com`, `reddit.com/search.json`, `old.reddit.com` (r/WindowsOnArm), `discourse.pi64.win` (the WoA community forum), and `gist.github.com` as HTML (only its `raw` endpoint worked). Stack Overflow/Superuser were not reachable for this query.
- `mcb30`'s patched QEMU (the `smc`-as-no-op change for `virt`) was never located as a public branch, fork or patch; only referenced in prose. The Fedora `arm-trusted-firmware` PR he cites (`src.fedoraproject.org/rpms/arm-trusted-firmware/pull-request/7`) was not fetched, so its rejection is only reported second-hand here.
