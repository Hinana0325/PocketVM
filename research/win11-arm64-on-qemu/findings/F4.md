# F4: Alternative machine types, firmware and CPU configurations for running Windows ARM64 under QEMU, including TPM/Secure Boot emulation and version dependence.

## Findings

### [1] No QEMU machine type is documented "for Windows"; `virt` is the board every working Windows-ARM64 configuration uses, and QEMU's own docs describe it as the default choice for running an OS guest.
- quote: "The `virt` board is a platform which does not correspond to any real hardware; it is designed for use in virtual machines. It is the recommended board type if you simply want to run a guest such as Linux"
- url: https://www.qemu.org/docs/master/system/arm/virt.html
- source_type: primary
- published: unknown (QEMU master docs, version 11.1.50)
- confidence: high

### [2] `sbsa-ref` is the only real alternative machine, and every documented fact about it argues against the Windows path: it is scoped to firmware development and OS standards-compliance testing, its device set is deliberately non-virtio (AHCI CDROM/HDD, XHCI, e1000e, Bochs display — no virtio-gpu, no virtio-blk), it needs a firmware image built specifically for its fixed hardware layout (TF-A `bl1.bin`/`fip.bin` plus edk2 256 MiB `SBSA_FLASH0/1.fd`), it never uses host acceleration, and neither the QEMU board doc nor the edk2 SbsaQemu platform README mentions Windows, TPM or Secure Boot at all.
- quote: "It is intended to be a machine for developing firmware and testing standards compliance with operating systems." / "CDROM and hard disc on AHCI bus" / "Bochs display adapter on PCIe bus" / "Sbsa-ref machine does not use any HW acceleration of your platform, even if you run it on ARM64 platform." / "truncate -s 256M SBSA_FLASH[01].fd"
- url: https://www.qemu.org/docs/master/system/arm/sbsa.html and https://github.com/tianocore/edk2-platforms/blob/master/Platform/Qemu/SbsaQemu/Readme.md
- source_type: primary
- published: unknown (QEMU master docs 11.1.50; edk2-platforms master, both retrieved 2026-10-23)
- confidence: high

### [3] Windows 11 requires UEFI Secure Boot capability plus TPM 2.0 on bare metal and a vTPM on a VM, so TPM/Secure Boot are Windows-side requirements no machine type avoids — but the standard community procedure bypasses the check rather than satisfying it.
- quote: "**System firmware**: UEFI, Secure Boot capable." / "**TPM**: Trusted Platform Module (TPM) version 2.0." / VM: "General settings: Secure boot capable, virtual TPM enabled."
- url: https://learn.microsoft.com/en-us/windows/whats-new/windows-11-requirements
- source_type: primary
- published: 2026-07-14 (ms.date; page updated 2026-07-21)
- confidence: high

### [4] QEMU does support a TPM on arm `virt` (`-device tpm-tis-device` fed by an swtpm backend), its TPM documentation names Windows 11 ARM64 as the guest that needs the ARM PPI region, and turning PPI off is not survivable for that guest — Windows then fails TPM startup on every boot.
- quote: "Both an ISA device and a sysbus device are available. The former is used with pc/q35 machine while the latter can be instantiated in the Arm virt machine." / "The ARM virt machine supports PPI for `tpm-tis-device` as defined in the PPI specification." / "Without PPI, guest operating systems such as Windows 11 ARM64 will log errors when attempting to query TPM Physical Presence capabilities via the ACPI `_DSM` method."
- url: https://www.qemu.org/docs/master/specs/tpm.html
- source_type: primary
- published: unknown (QEMU master docs, version 11.1.50)
- confidence: high

### [5] PPI is a fresh addition to the ARM TPM device (added in 2026) and its guest-visible region is only 0x400 bytes, which is not a host-page multiple: that misalignment aborts QEMU outright under HVF on 16 KiB-page hosts, whereas the identical command line under `accel=tcg -cpu cortex-a72` boots — so on a 4 KiB-page TCG host the TPM configuration is not the failure.
- quote: "The same command with `accel=tcg -cpu cortex-a72` boots; without the TPM device, HVF boots; with `ppi=off` HVF boots. So the failing piece is the PPI region that `tpm-tis-device` gained in 2026." / "`ppi=off` is not a usable workaround for a Windows guest: Windows 11 ARM64 then logs tpm.sys Event ID 15 (\"non-recoverable error in the TPM hardware\") on every boot and `Get-Tpm` fails with 0x80284001"
- url: https://gitlab.com/qemu-project/qemu/-/work_items/4663
- source_type: secondary
- published: 2026-10-08 (upstream tracker; reporter validated a one-line fix)
- confidence: high

### [6] The QEMU version does matter for Windows ARM64: a triaged upstream bug has a Windows 11 ARM64 guest stop after the Windows Boot Manager progress bar completes with exactly one vCPU spinning at 100 % forever on QEMU 10.2.1, while the same disk image, firmware and machine configuration boot fine on QEMU 6.2.0 on identical hardware.
- quote: "the Boot Manager progress bar completes, then one vCPU spins at 100 % forever and the guest agent never comes up. The same disk image, firmware and libvirt-generated configuration boot fine on QEMU 6.2.0 on identical hardware."
- url: https://gitlab.com/qemu-project/qemu/-/work_items/4411
- source_type: secondary
- published: 2026-09-04 (upstream tracker; labelled `GuestOS ➤ Windows`, `Target ➤ ARM`, `Workflow::Triaged`)
- confidence: high

### [7] In that upstream case the trigger is a PCIe root port and the remedy is a single device property: Windows' root-port interrupt handler livelocks on the permanently asserted "Command Completed" slot status of a hot-plug-capable `pcie-root-port`, `hotplug=off` makes the guest boot, and the reporter ruled out firmware build (three AAVMF versions), NVRAM contents, cache mode, vCPU count/topology, the `virt-6.2` machine type on QEMU 10.2.1, `pmu=off` and GIC/CPU model — suspecting QEMU 8.0 commit 1768e97b.
- quote: "Setting `hotplug=off` on all root ports (libvirt `<target hotplug='off'/>`) makes the guest boot normally; nothing else needs to change." / "the only guest-visible slot-code change since 6.2 I can find is commit 1768e97b (\"pcie: set power indicator to off on reset by default\", QEMU 8.0)"
- url: https://gitlab.com/qemu-project/qemu/-/work_items/4411
- source_type: secondary
- published: 2026-09-04
- confidence: medium

### [8] The community's canonical guide (70 comments, last updated 2026-09-21) treats pure TCG as a supported install path and prescribes `-cpu neoverse-n1` there, and it documents both hard QEMU version floors and a CPU/machine combination that stops Windows booting: QEMU >= 8.1 for `SCR_HXEN`, QEMU < 8.2 trapping `HDFGRTR_EL2` accesses to a non-existent EL3, and `-machine virt,virtualization=on -cpu max` breaking Windows because the guest hypervisor path expects EL3.
- quote: "When following this guide on a host not capable of aarch64 virtualization, replace `-cpu host -accel kvm` with `-cpu neoverse-n1` (faster to emulate then `-cpu max`)." / "QEMU < 8.1 is missing also `SCR_HXEN` and probably others, so make sure to use at least 8.1.0." / "For QEMU < 8.2.0 you either need to use `-cpu neoverse-n1` or apply … to avoid that accesses to `HDFGRTR_EL2` trap to EL3 which does not exist -> stuck." / "Windows no longer boots if the hypervisor is enabled. With WinDbg attached it complains about unexpected register values which indicate that it expects the CPU to have EL3."
- url: https://gist.github.com/Vogtinator/293c4f90c5e92838f7e72610725905fd (README.md and WSL2.md, retrieved via https://api.github.com/gists/293c4f90c5e92838f7e72610725905fd)
- source_type: community
- published: 2022-11-10, updated 2026-09-21
- confidence: medium

### [9] That guide bypasses TPM and Secure Boot with `LabConfig` registry values rather than providing them, whereas the combination Windows actually *accepts* in 2026 is a matching Secure Boot AAVMF pair plus swtpm: Windows 11 ARM64 installed and booted on QEMU 10.1.2 (HVF) with swtpm 0.10.1, `tpm-tis-device`, an nvme disk and `ramfb` (used because "Windows ARM has no inbox virtio-gpu driver"), with the firmware lookup accepting only `AAVMF_CODE.secboot.fd` + `AAVMF_VARS.ms.fd`.
- quote: "create a key (aka. folder) called `LabConfig` and inside that three DWORDs `BypassTPMCheck`, `BypassSecureBoot` and `BypassSecureBootCheck` with the value 1. Alternatively you can also use a SB-enabled OVMF as bios and provide a TPM, but I haven't tried that" / "Manual: Windows 11 ARM64 installed and booted on an M4 Mac Studio with QEMU 10.1.2 (HVF) and swtpm 0.10.1; TPM and Secure Boot checks pass" / "`find_windows_arm` only accepts the Secure Boot pair `AAVMF_CODE.secboot.fd` + `AAVMF_VARS.ms.fd`"
- url: https://gist.github.com/Vogtinator/293c4f90c5e92838f7e72610725905fd and https://github.com/trycua/cua/pull/5506 (both retrieved via api.github.com)
- source_type: community
- published: 2026-10-19 (cua PR); gist 2022-11-10, updated 2026-09-21
- confidence: high

### [10] A second, independent project reports a Secure-Boot-firmware regression at QEMU 11 specifically: bundling QEMU 10.2.2 with Ubuntu's `AAVMF_CODE.secboot.fd` (2025.11) meant the "Secure Boot guest actually worked", while the same firmware on QEMU 11.1.1 + HVF froze at TianoCore with ~100 % CPU in every display arrangement and QEMU 11 additionally required `tpm-tis-device,ppi=off` to start at all on that host.
- quote: "| Alpha pkg: bundled **QEMU 10.2.2** + AAVMF **2025.11** | HVF | ramfb + virtio-gpu | Secure Boot guest actually worked |" / "QEMU 11 also needed, independently of GOP: … `tpm-tis-device,ppi=off` (PPI MMIO unaligned → `HV_BAD_ARGUMENT` at `hvf-all.c:123`)"
- url: https://github.com/pmdroid/barkvisor/issues/564 and https://github.com/pmdroid/barkvisor/issues/565 (via api.github.com search)
- source_type: community
- published: 2026-09-08
- confidence: medium

### [11] The machine type leaks into what Windows reports about the PC — and hence into what compatibility tooling sees — while the ACPI OEM fields are overridable: Windows shows the CPU as `virt-10.0` on `-machine virt`, an earlier report has PC Health Check rejecting `virt-8.0`, and QEMU exposes `x-oem-id` / `x-oem-table-id` to rewrite the ACPI OEMID and OEM Table ID.
- quote: "Windows sees the processor as 'virt-10.0', model 'AVM Virtual Machine', BIOS version 0.0.0. UTM had a similar report where PC Health Check rejected 'virt-8.0'." / "`x-oem-id` Set string (up to 6 bytes) to override the default value of field OEMID in ACPI table header."
- url: https://github.com/allisonfm85/accessible-virtual-machine/issues/17 (via api.github.com) and https://www.qemu.org/docs/master/system/arm/virt.html
- source_type: community (issue) plus primary (QEMU docs)
- published: 2026-10-09 (issue)
- confidence: medium

### [12] GICv5 is unusable for a Windows guest on `virt`: QEMU 11.1 ships `-machine virt,gic-version=x-5` as experimental and it is not exposed via ACPI at all, while Windows ARM64 boots via ACPI — so GICv3 (with its ITS MSI controller) remains the only relevant interrupt controller, and `acpi=on/off/auto` is the corresponding machine knob.
- quote: "the GICv5 is not exposed to the guest via ACPI tables, only via DTB" / "`acpi` Set `on`/`off`/`auto` to enable/disable ACPI."
- url: https://www.qemu.org/docs/master/system/arm/virt.html
- source_type: primary
- published: unknown (QEMU master docs, version 11.1.50)
- confidence: high

## Dead ends
- Bing (both `cn.bing.com` and `bing.com` with `setmkt=en-US`) returned unrelated localized results (douyin/zhihu/tiktok pages) for every English query in this session; DuckDuckGo HTML/lite, Mojeek and Brave all failed at transport/DNS level. All search had to go through the GitHub and GitLab REST search APIs.
- `wiki.qemu.org` (per-release ChangeLog pages) sits behind an Anubis JS challenge and could not be read, so per-release aarch64 notes could not be cited directly; version dependence had to be established from upstream issues and community guides instead.
- `raw.githubusercontent.com`, `cdn.jsdelivr.net` and `gist.github.com` are unreachable from this environment (SSRF/DNS failures); their content was obtained through the `api.github.com` equivalents.
- GitHub issue search for `sbsa-ref` + Windows returned only an unrelated Rust QEMU reimplementation (`tamnd/ruvm`); no report of Windows ARM64 being run on `sbsa-ref` exists in the sources reachable here. Likewise, no QEMU or edk2 document names a machine type "for Windows".
- No source attributes a Windows ARM64 *early-kernel* halt (exception handler `b .` after a Data Abort with FAR=0) to a machine type, CPU model or firmware build. The closest upstream analogues are post-boot-manager stalls (#4411) and firmware freezes (barkvisor #564) — same visible shape (guest stops, one vCPU at 100 %), different root causes.

## Suggested follow-ups
- Does PocketVM's argv contain any `pcie-root-port` (or rely on default root ports)? Testing `hotplug=off` on every root port is a one-line change motivated by QEMU #4411, where that single device property is the only difference between "hangs forever with one vCPU at 100 %" and "boots".
- Bisect the same argv across QEMU 6.2 / 8.x / 10.2 / 11.1 on the x86_64 TCG host: #4411 shows a real Windows-ARM64 boot regression introduced between 6.2 and 10.2.1, and #564/#565 show a separate one at 11.x on the Secure Boot firmware path.
- Retry with the matching Secure Boot firmware pair (`AAVMF_CODE.secboot.fd` + `AAVMF_VARS.ms.fd` from one edk2 build) plus `swtpm` + `tpm-tis-device` and *no* `LabConfig` bypass, under aarch64 TCG: the only 2026-verified "Windows accepts it" combination uses exactly that set, and nothing found here tests it under TCG.
