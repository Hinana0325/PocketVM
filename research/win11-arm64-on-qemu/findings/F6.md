# F6: What Windows on ARM requires from its platform/firmware (UEFI, ACPI, TPM, timers, interrupt model) and why generic QEMU `virt` may be insufficient.

## Findings

### [1] Windows does not treat ACPI as optional on SoC platforms: the ACPI *hardware* spec is not required, but much of the ACPI *software* spec is required, table formats come from ACPI 5.0, and the OS only finds the root tables through UEFI's EFI system table.
- quote: "Implementation of the Advanced Configuration and Power Interface (ACPI) Hardware Specification isn't required on SoC-based platforms, but much of the ACPI Software Specification is (or can be) required." / "Windows will use the EFI system table to locate the RSDP, as described in section 5.2.5.2, \"Finding the RSDP on UEFI Enabled Systems\", of the ACPI 5.0 specification."
- url: https://learn.microsoft.com/en-us/windows-hardware/drivers/bringup/acpi-system-description-tables
- source_type: primary
- published: 2025-04-30 (updated 2025-07-18)
- confidence: high

### [2] Windows defines an explicit required table set reachable from the RSDT/XSDT (FADT, MADT, optional CSRT, DBG2, BGRT, FPDT, DSDT, optional SSDTs), prefers the XSDT when both exist, and demands a debug port on every system.
- quote: "Specifically, this table contains pointers to the following tables: The Fixed ACPI Hardware Table (FADT) / The multiple interrupt controller table (MADT) / Optionally, the Core System Resource Table (CSRT) / The Debug Port Table 2 (DBG2) / The Boot Graphics Resource Table (BGRT) / The Firmware Performance Data Table (FPDT) / The base system description table (DSDT) / Optionally, additional system description tables (SSDT)" and "Microsoft requires a debug port on all systems."
- url: https://learn.microsoft.com/en-us/windows-hardware/drivers/bringup/acpi-system-description-tables
- source_type: primary
- published: 2025-04-30 (updated 2025-07-18)
- confidence: high

### [3] For Arm64, Windows' interrupt model is the GIC described through MADT descriptors (ACPI 5.0 GIC and GIC Distributor structures, which Windows has inbox support for), and the boot processor's GIC entry must be first in the descriptor list; the Arm64 timer model is the ARM generic timer surfaced through GTDT, which Windows also supports inbox.
- quote: "For Arm-based SoC platforms, ACPI 5.0 adds descriptors for the Arm Holdings' Generic Interrupt Controller (GIC) and GIC Distributor. Windows includes inbox support for the GIC and GIC Distributor." / "The GIC corresponding to the boot processor must be the first entry in the list of interrupt controller descriptors." / "For Arm systems that utilize the GIT timer, ACPI's GTDT can be used to leverage the built-in support for the GIT in Windows."
- url: https://learn.microsoft.com/en-us/windows-hardware/drivers/bringup/acpi-system-description-tables
- source_type: primary
- published: 2025-04-30 (updated 2025-07-18)
- confidence: high

### [4] Windows has no generic software path for non-standard SoC core resources: any shared block that industry standards do not cover (the doc's own example is DMA controllers) must be declared in a CSRT that is present in the RSDT *and* mirrored as an ACPI namespace device, because support ships only as a SoC-vendor HAL extension DLL — and those DLLs are what Windows Update services.
- quote: "until the industry converges on DMA controller interface standards, there's a need to support some non-standard devices in the operating system. Windows supports the concept of HAL extensions to address this issue." / "each resource group described in the CSRT must also be represented as a device within the platform's ACPI namespace"
- url: https://learn.microsoft.com/en-us/windows-hardware/drivers/bringup/acpi-system-description-tables
- source_type: primary
- published: 2025-04-30 (updated 2025-07-18)
- confidence: high

### [5] The mandated firmware baseline is UEFI (spec version 2.3.1 Errata or higher) with UEFI Secure Boot shipping enabled by default; Windows 11's minimum hardware summary lists "System firmware REQUIRED: UEFI" and "UEFI Secure Boot (enabled by default) REQUIRED".
- quote: "System firmware must be compliant with the UEFI Specification Version 2.3.1 Errata or higher. Windows 11 devices must ship with UEFI Secure Boot enabled by default."
- url: https://download.microsoft.com/download/7/8/8/788bf5ab-0751-4928-a22c-dffdc23c27f2/Minimum%20Hardware%20Requirements%20for%20Windows%2011.pdf (text extracted locally; companion page https://learn.microsoft.com/en-us/windows-hardware/design/minimum/minimum-hardware-requirements-overview)
- source_type: primary
- published: 2021-06 (doc revision "June 2021"; page ms.date 2021-06-24)
- confidence: high

### [6] TPM requirements are specified at the protocol level, not just "have a TPM 2.0": ISO/IEC 11889:2015 or TCG TPM 2.0 Library compliance, present and enabled by default, SHA-256 PCR banks 0–23, TPM2_HMAC support, and an EK certificate either pre-provisioned or retrievable at first boot — but Microsoft documents an exemption for special-purpose/commercial/custom-image systems that need not ship with TPM enabled, which is why an installer can run on a TPM-less VM.
- quote: "All device models, lines or series must implement and be in compliance with the International Standard ISO/IEC 11889:2015 or the Trusted Computing Group TPM 2.0 Library and a component which implements the TPM 2.0 must be present and enabled by default." / "It must ship with SHA-256 PCR banks and implement PCRs 0 through 23 for SHA-256." / "Upon approval from Microsoft, OEM systems for special purpose commercial systems, custom order, and customer systems with a custom image are not required to ship with a TPM support enabled."
- url: https://download.microsoft.com/download/7/8/8/788bf5ab-0751-4928-a22c-dffdc23c27f2/Minimum%20Hardware%20Requirements%20for%20Windows%2011.pdf
- source_type: primary
- published: 2021-06
- confidence: high

### [7] For ARM64 specifically, the documented CPU contract is ≥2 cores plus the ARMv8.1 atomic (LSE) extension — 64-bit ARMv8.0 cores are not sufficient — which matches the need for a QEMU CPU model newer than cortex-a72.
- quote: "Devices that run Windows 11 require a 1 GHz or faster processor that meets the following requirements. x Supports 2 Processor Cores x Compatible with the x64 or ARM64 instruction set x Supports PF_ARM_V81_ATOMIC_INSTRUCTIONS_AVAILABLE instruction set (for ARM64 processor)"
- url: https://download.microsoft.com/download/7/8/8/788bf5ab-0751-4928-a22c-dffdc23c27f2/Minimum%20Hardware%20Requirements%20for%20Windows%2011.pdf
- source_type: primary
- published: 2021-06
- confidence: high

### [8] Windows' own minimum spec requires DMA protection — Memory Access Protection / Kernel DMA Protection (kDMA), with PCIe Native Control enabled — on any device exposing external PCIe-capable ports, i.e. an IOMMU/SMMU-gated device model is part of the platform contract, not an optional security extra.
- quote: "Device with external PCIe capable ports (e.g. Thunderbolt) must support Memory Access Protection or Kernel DMA Protection (kDMA) and enabled/opted-in by default."
- url: https://download.microsoft.com/download/7/8/8/788bf5ab-0751-4928-a22c-dffdc23c27f2/Minimum%20Hardware%20Requirements%20for%20Windows%2011.pdf
- source_type: primary
- published: 2021-06
- confidence: high

### [9] VBS (the layer Win11 leans on for memory integrity/HVCI) adds a hard platform list: a Windows hypervisor on a 64-bit CPU with virtualization extensions and SLAT, **all** DMA-capable I/O devices behind an IOMMU/SMMU (naming "Arm64 SMMUs"), TPM 2.0, firmware implementing the SMM-protection flags of the WSMT ACPI table, UEFI v2.6 Memory Attributes Table with read-only-executable-consistent page attributes, Secure MOR v2, and Secure Boot enabled.
- quote: "All I/O devices capable of DMA must be behind an IOMMU or SMMU. An IOMMU can be used to enhance system resiliency against memory attacks." / "Firmware must implement the protections described in the WSMT specification, and set the corresponding protection flags as described in the specification to report compliance with these requirements to the operating system." / "Secure Boot must be enabled on devices leveraging VBS."
- url: https://learn.microsoft.com/en-us/windows-hardware/design/device-experiences/oem-vbs
- source_type: primary
- published: 2023-03-17 (updated 2025-09-04)
- confidence: high

### [10] iPXE's maintainer states Windows on ARM *assumes* EL3 exists with ATF (or equivalent Secure World firmware) able to answer `smc`; QEMU's `virt` machine type provides neither, and the only reason Windows ARM64 sometimes boots there is that KVM emulates `smc` incorrectly as a no-op — under TCG `smc` is emulated correctly and crashes the guest. This is the closest published statement to PocketVM's symptom (correct TCG emulation, guest dies early) and it is a *firmware/exception-level* requirement, not a device requirement.
- quote: "Windows on ARM assumes that EL3 is supported and that ATF (or some other Secure World firmware) is present and able to respond to `smc` instructions, but this isn't the case on the QEMU `virt` machine type. If you're using ARM KVM then the `smc` instruction gets emulated incorrectly as a no-op, and this bug causes the system to actually boot correctly. If you're using TCG (e.g. running `qemu-system-aarch64` on an x86 box), then the `smc` instruction gets emulated correctly and crashes the VM."
- url: https://github.com/ipxe/wimboot/issues/4
- source_type: community
- published: 2026-03-18
- confidence: medium

### [11] QEMU itself frames the `virt` board as deliberately unrepresentative — not real hardware, and the recommended board "if you simply want to run a guest such as Linux" — and its defaults leave the Windows-relevant platform pieces off: `virtualization=off`, `secure=off` (no EL3/TrustZone), `iommu=none` (no SMMUv3), ACPI on/off/auto, SBSA watchdog only as an optional device.
- quote: "The ``virt`` board is a platform which does not correspond to any real hardware; it is designed for use in virtual machines. It is the recommended board type if you simply want to run a guest such as Linux and do not care about reproducing the idiosyncrasies and limitations of a particular bit of real-world hardware." / "virtualization ... The default is ``off``." / "secure ... The default is ``off``." / "iommu ... ``none`` Don't create an IOMMU (the default)"
- url: https://gitlab.com/qemu-project/qemu/-/raw/master/docs/system/arm/virt.rst
- source_type: primary
- published: unknown (upstream master, fetched 2026-10-23)
- confidence: high

### [12] Reading `hw/arm/virt-acpi-build.c` confirms the actual table surface generic `virt` gives a Windows guest: FADT rev 6 with HARDWARE_REDUCED_ACPI set and ARM boot-arch flags (PSCI compliant, PSCI-over-HVC when virtualization is on), MADT ("APIC") rev 4 with GICC/GICD descriptors, GTDT rev 3 carrying Secure-EL1/NonSecure-EL1/Virtual timer GSIVs, DBG2, DSDT rev 2, SPCR rev 2, IORT rev 5, SRAT only when NUMA nodes exist, MCFG with PCIe, WDAT only when `-device sbsa-gwdt,wdat=on` is used, and MSFT0101 in DSDT when a TPM is attached — but there is **no PPTT builder and no WSMT anywhere in the file**, and no CSRT.
- quote: `AcpiTable table = { .sig = "GTDT", .rev = 3, ...` ; `AcpiTable table = { .sig = "APIC", .rev = 4, ...` ; `.flags = 1 << ACPI_FADT_F_HW_REDUCED_ACPI` ; `fadt.arm_boot_arch = ACPI_FADT_ARM_PSCI_COMPLIANT | ACPI_FADT_ARM_PSCI_USE_HVC;` (absence of PPTT/WSMT verified by full-file search)
- url: https://gitlab.com/qemu-project/qemu/-/raw/master/hw/arm/virt-acpi-build.c
- source_type: primary
- published: unknown (upstream master, fetched 2026-10-23)
- confidence: high

### [13] Counter-evidence that `virt` is *sufficient*: UTM's maintained guide installs Windows 11 ARM64 in QEMU `virt` (its "Virtualize" mode) and relies on TPM 2.0 + Secure Boot being enabled for the guest to pass Windows 11's checks, while documenting that Windows lacks inbox drivers for this generic device model (network only works after installing the separately provided guest-tools/virtio driver pack) and that 24H2 specifically has a graphics-driver incompatibility causing a black screen.
- quote: "On newer versions of UTM, Secure Boot and TPM should be enabled automatically." / "Make sure you installed the SPICE guest tools, which includes the network drivers." / "Windows 11 24H2 has a compatibility issue with the graphics drivers that are provided by the UTM guest tools ISO."
- url: https://docs.getutm.app/guides/windows/
- source_type: secondary
- published: unknown (undated page, references 24H2)
- confidence: medium

## Dead ends
- General web search was effectively unavailable in this environment: `duckduckgo.com/html`, `lite.duckduckgo.com`, `search.brave.com`, `mojeek.com`, `r.jina.ai`, `raw.githubusercontent.com` and `cdn.jsdelivr.net` all returned transport errors, and Bing (both the rendered page and `&format=rss`) returned a query-independent, China-localized result set (identical 10 hits for completely different queries), so no SERP could be trusted.
- `learn.microsoft.com/api/search` accepted queries but its semantic mode returned generic Windows landing pages rather than the ARM64 ACPI/firmware requirements doc; the ACPI requirements doc was reached by direct URL instead.
- `api.github.com/search/issues` returned unfiltered, unrelated results (the query appeared to be dropped), so GitHub could not be used as a discovery engine — only for direct issue/comment reads.
- No Microsoft document was found that states an explicit minimum ACPI *revision* for Arm64 (the ACPI page anchors on ACPI 5.0 table definitions and the min-hardware PDF never mentions ACPI at all); nor was any Microsoft text found that states GICv2 is unsupported, so the "Windows requires GICv3/ITS" idea is unverified and should not be claimed.
- The WHCP requirements document that the min-hardware PDF defers to (aka.ms/whcp, which is where per-version firmware/ACPI test requirements live) was not fetched — its PDF form could not be turned into text through any working route in this environment.

## Suggested follow-ups
- Get the Windows Hardware Compatibility Program requirements text (aka.ms/whcp) for the System.Fundamentals.Firmware.* requirements to see whether PPTT/IOMMU/ACPI revision are explicitly required for Arm64, and whether they are test-enforced versus OEM-declared.
- Test the EL3/`smc` hypothesis directly: run the same ISO with `-machine virt,secure=on` plus an ATF/EL3 blob (or the `sbsa-ref` machine, which ships ATF) and see whether the FAR=0 `b .` halt moves or disappears — this is the one published mechanism that explains "correct on hardware, crashes on TCG".
- Determine whether QEMU, at least on x86_64 hosts with `-cpu cortex-a76` + edk2 + vTPM + Secure Boot and no ATF, was ever shown to pass WinPE with the *same* ISO build in question (QEMU version-specific regression check), to separate "virt is non-conformant" from "this QEMU release/ISO combination is broken".
