# F7: Alternative routes to a usable Windows ARM64 instance (image preparation, more permissive Windows editions, required hypervisor paths).

## Findings

### [1] Microsoft publicly ships a Windows 11 Arm64 ISO (multi-edition, current release "Windows 11 2026 Update | Version 26H2") and its download page explicitly frames it as VM media, so clean arch-correct install media are freely obtainable without Insider or OEM channels.
- quote: "This option is for users that want to create a Windows 11 on Arm virtual machine on supported hardware using an ISO file or to install Windows 11 on Arm directly without a DVD or USB flash drive."
- url: https://www.microsoft.com/en-us/software-download/windows11arm64
- source_type: primary
- published: unknown (page fetched 2026-10-23; page states current release = Windows 11 2026 Update, version 26H2)
- confidence: high

### [2] There is no equivalent public Microsoft ARM64 media path for Windows 10: the Windows 10 download page offers only the Media Creation Tool / Update Assistant with 64-bit vs 32-bit choices, while Arm64 media exist only under the Windows 11 pages — so a Windows 10 Arm64 experiment must start from non-official media (e.g. UUP-dump-built ISOs).
- quote: "**64-bit or 32-bit processor (CPU)**. You'll create either a 64-bit or 32-bit version of Windows 10."
- url: https://www.microsoft.com/en-us/software-download/windows10
- source_type: primary
- published: unknown (page fetched 2026-10-23; page notes Windows 10 end of support 2025-10-14)
- confidence: medium

### [3] Microsoft's own Windows Server processor-requirements table has no Arm64 column at all (only Intel, AMD, Hygon) for Windows Server 2012 R2 through Windows Server 2025, so "run Windows Server Arm64 instead" is not a documented, supportable substitute platform.
- quote: "| Windows Edition | Intel Processors | AMD Processors | Hygon Processors^[7]^ |"
- url: https://learn.microsoft.com/en-us/windows-hardware/design/minimum/windows-processor-requirements
- source_type: primary
- published: 2026-09-03 (page `ms.date: 2026-08-31`, `updated_at: 2026-09-03`)
- confidence: high

### [4] QEMU natively reads and writes the Hyper-V VHDX image format (subformats `dynamic` default and `fixed`), so a Microsoft- or third-party-provided Windows ARM64 VHDX can be booted directly by QEMU or converted with `qemu-img` on the target machine; only qcow2 additionally supports VM snapshots.
- quote: "Hyper-V compatible image format (VHDX). ... Specifies which VHDX subformat to use. Valid options are ``dynamic`` (default) and ``fixed``."
- url: https://gitlab.com/qemu-project/qemu/-/raw/master/docs/system/qemu-block-drivers.rst.inc
- source_type: primary
- published: unknown (QEMU master docs, fetched 2026-10-23)
- confidence: high

### [5] DISM's documented offline workflow applies an image into an attached, partitioned, formatted VHDX (`/Apply-Image /ApplyDir:`), which is exactly the "build the system volume outside WinPE and boot it" route — supported and documented, with `/Compact` and `/EA` variants available.
- quote: "This option doesn't support applying an image from a virtual hard disk (VHD), though you can use this command to apply images to a .vhdx file that's been attached, partitioned, and formatted."
- url: https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/dism-image-management-command-line-options-s14
- source_type: primary
- published: 2024-06-06 (`updated_at`), `ms.date: 2021-08-24`
- confidence: high

### [6] Generalizing is mandatory, not optional, before a captured image is deployed — and Microsoft provides `/mode:vm` specifically for a VHD that will be redeployed on the same hypervisor, which is the cheaper variant of the "install elsewhere, then copy the disk" route.
- quote: "Before you can deploy a Windows image to new PCs, you have to first generalize the image."
- url: https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/sysprep--generalize--a-windows-installation
- source_type: primary
- published: 2021-12-15 (`updated_at`)
- confidence: high

### [7] wimlib (v1.14.5, released 2026-01-29) is an open-source, cross-platform replacement for DISM/WIMGAPI that applies WIM and ESD images from Linux/macOS (NTFS-3G integration, optional FUSE read-write mounting, experimental Windows ARM64 binaries), so the ARM64 `install.wim` can be applied offline without any Windows host.
- quote: "Allows deployment of Windows operating systems from non-Windows operating systems such as Linux."
- url: https://wimlib.net/
- source_type: primary
- published: 2026-01-29 (current release date on the fetched page)
- confidence: high

### [8] Windows 11 hard-requires TPM 2.0 and Secure-Boot-capable UEFI firmware, and Microsoft's VM guidance requires Gen-2 VMs with virtual TPM plus Secure Boot (Azure: trusted launch), so a QEMU machine without an emulated TPM/Secure Boot chain can only proceed via Microsoft-documented bypass keys — a provisioning-stage obstacle, not a kernel-stage one.
- quote: "**System firmware**: UEFI, Secure Boot capable."
- url: https://learn.microsoft.com/en-us/windows/whats-new/windows-11-requirements
- source_type: primary
- published: 2026-07-21 (`updated_at`), `ms.date: 2026-07-14`
- confidence: high

### [9] UTM's Arm Windows 11 guide records both the documented installer bypass (LabConfig `BypassTPMCheck`/`BypassSecureBootCheck`) and a minimum ARM64 build floor of 21390 — older ARM64 Windows builds BSOD with `SYSTEM_THREAD_EXCEPTION_NOT_HANDLED`, which is precisely where Windows 10 Arm64 (builds 19041–19044) sits.
- quote: "You are using a version of Windows that is too old. The build number should be 21390 or higher."
- url: https://docs.getutm.app/guides/windows/
- source_type: community
- published: unknown
- confidence: medium

### [10] UTM's documented Windows 11 Arm installation path is the "Virtualize" (Apple Virtualization framework) wizard path, and UTM positions its JIT-less interpreter build as suitable only for "older operating systems such as DOS or stripped down operating systems such as Alpine Linux" — i.e. in practice ARM64 Windows guests are run under a hypervisor, never under a plain interpreter.
- quote: "UTM SE is a stripped down version of UTM which does not support JIT and uses a slower interpreter for emulation. It can be used to run older operating systems such as DOS or stripped down operating systems such as Alpine Linux."
- url: https://docs.getutm.app/installation/ios/
- source_type: community
- published: unknown
- confidence: medium

### [11] All current Windows-11-ARM64-under-QEMU tooling found on GitHub is hypervisor-accelerated rather than TCG: "QEMU+HVF" on Apple silicon or "QEMU + Hypervisor.framework", with no TCG-based Windows 11 ARM64 runner among the results.
- quote: "Zero-touch Windows 11 ARM VMs on Apple silicon via QEMU+HVF — SSH/CI-ready (dockur-style, native)"
- url: https://github.com/search?q=windows+11+arm64+qemu&type=repositories
- source_type: community
- published: unknown (repository search results, fetched 2026-10-23; also lists "Scriptable Windows 11 ARM64 VM on a Mac (Apple Silicon) with QEMU + Hypervisor.framework")
- confidence: medium

### [12] QEMU's `sbsa-ref` machine is an alternative to `virt` that exposes AHCI + XHCI + E1000E + a Bochs display and a GICv3, but it is a static platform that requires firmware built for that exact layout, and its documentation never mentions Windows as a supported target (it is scoped to "developing firmware and testing standards compliance with operating systems").
- quote: "``sbsa-ref`` is a static system that reports a very minimal devicetree to the firmware for non-discoverable information about system components."
- url: https://gitlab.com/qemu-project/qemu/-/raw/master/docs/system/arm/sbsa.rst
- source_type: primary
- published: unknown (QEMU master docs, fetched 2026-10-23)
- confidence: medium

## Dead ends
- Bing is geo-locked to the CN edition on this network: every technical query returned Microsoft consumer download/百度百科/CSDN pages, and `site:` operators were ignored; unusable for English technical discovery.
- `html.duckduckgo.com`, `lite.duckduckgo.com`, `www.mojeek.com`, `search.brave.com` all failed with transport errors from this network; no alternative web-search endpoint succeeded, so discovery had to run through GitHub's search UI and Microsoft's Learn search API.
- GitLab issue search is closed to anonymous callers: `/api/v4/projects/11167699/search?scope=issues` returns 401, and `issues?search=` ignores the term (it matches the issue-template boilerplate "Windows 10 21H1"), so the upstream QEMU tracker could not be searched for Windows-on-Arm boot failures.
- The Windows Insider Preview ARM64 download page (and the Windows Server Insider page) is membership-gated ("To access this page, you need to be a member of the Windows Insider program"), so whether a prebuilt, generalized Windows 11 ARM64 VHDX is currently offered could not be verified.
- The "Minimum Hardware Requirements for Windows 11" (and Windows 10) PDFs are only served as compressed PDF object streams; webfetch returned raw, non-extractable PDF bytes, so the exact Arm64 CPU clause (Armv8.1/LSE atomics) and the Windows 10 equivalent could not be read and are therefore not cited here.
- `github.com/exusxt/ARM64onX86` ("running Windows 11 ARM64 virtual machines on x86 PCs", i.e. the closest TCG-host analogue) is an empty 1-commit stub with a README containing nothing but its own one-line description — no evidence obtainable.
- `learn.microsoft.com/api/search` is semantic rather than literal and returned mostly consumer/Visual Studio pages; no Microsoft page stating whether DISM can apply/servicing an image whose architecture differs from the running host was located.
- No source at all was found reporting a TCG (or `-accel tcg`) Windows ARM64 boot — neither success nor failure — so the question "does anyone boot Windows on Arm under TCG?" remains open in this angle.
