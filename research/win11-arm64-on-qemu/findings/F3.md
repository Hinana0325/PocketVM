# F3: QEMU upstream and community patch sets for Windows-on-ARM support, their maturity and maintenance status.

Scope note: there is no upstream QEMU branch, machine type or patch queue called "windows"/"WoA". What exists is (a) a small number of Windows-motivated ACPI additions that *did* land upstream, (b) one confirmed Windows-ARM64 boot regression against `virt` that was never fixed, (c) a Microsoft-adjacent downstream project (Open Device Partnership) that carries its own QEMU patch set and its own ACPI, and (d) host-side work that makes Windows-on-ARM a QEMU *host*. All evidence below is from primary sources (QEMU bug tracker, qemu-devel archive, QEMU master source via GitLab API, QEMU master docs, GitLab tracker API, GitHub API).

## Findings

### [1] The one concrete Windows-ARM64 boot regression against `virt` — the 256 MB high ECAM region — was reported in 2018, confirmed fixed only by disabling high ECAM, and never fixed upstream; the bug was auto-expired in 2021.
- quote: "Yeah it seems to be. Windows boots fine after I disable hi ECAM region."
- url: https://bugs.launchpad.net/qemu/+bug/1804961
- source_type: primary
- published: 2018-11-24 (bug); 2018-12-05 (confirmation); 2021-01-31 (expired)
- confidence: high
- detail: "qemu-system-aarch64: Windows 10 ARM64 BSoD on boot while using virt-3.0", reporter GH Cao (driver1998), symptom `ACPI_BIOS_ERROR (0x000000A5)`, Windows 10.0.17134.1, QEMU 3.0.0; virt-2.12 boots fine. Alex Bennée bisected it to commit `17ec075a651a` "hw/arm/virt: Use 256MB ECAM region by default" (Eric Auger, 2018-06-22) and noted the compat flag `vmc->no_highmem_ecam = true` in `virt_machine_2_12_options()`. Thomas Huth moved it to Incomplete (2020-12-01), Launchpad Janitor expired it (2021-01-31). No QEMU patch, quirk or machine flag was added for Windows.

### [2] The upstream machine knob that controls that exact behaviour is `highmem-ecam`, documented as `on` by default for every machine type later than `virt-3.0`; nothing in the `virt` option list is Windows-specific.
- quote: "highmem-ecam — Set `on`/`off` to enable/disable the high memory region for PCI ECAM. The default is `on` for machine types later than `virt-3.0`."
- url: https://www.qemu.org/docs/master/system/arm/virt.html
- source_type: primary
- published: unknown (QEMU master docs, manual for version 11.1.50)
- confidence: high
- detail: the full machine-option list on `virt` (`secure`, `virtualization`, `mte`, `highmem`, `compact-highmem`, `highmem-redists`, `highmem-ecam`, `highmem-mmio`, `gic-version`, `msi`, `its`, `iommu`, `ras`, `acpi`, `cxl`, `dtb-randomness`, `virtio-mmio-transports`, `x-oem-id`, `x-oem-table-id`) contains no Windows mode; `-cpu` list contains no `cortex-x*`/Snapdragon target. Practical consequence for PocketVM: Windows 11 on `virt` is expected to need `-machine virt,highmem-ecam=off` (the modern equivalent of the 2018 workaround), and `x-oem-id`/`x-oem-table-id` are the supported way to spoof ACPI OEM identity if a downstream needs it.

### [3] Windows-motivated ACPI table work *did* land upstream: QEMU master's arm `virt` ACPI builder now generates DBG2, SPCR, PPTT and GTDT, and can emit a WDAT table for the SBSA generic watchdog.
- quote: "/* FADT MADT PPTT GTDT MCFG SPCR DBG2 pointed to by RSDT */"
- url: https://gitlab.com/api/v4/projects/11167699/repository/files/hw%2Farm%2Fvirt-acpi-build.c/raw?ref=master
- source_type: primary
- published: unknown (file read 2026-10-23; QEMU master = 11.1.50)
- confidence: high
- detail: verified symbols in `hw/arm/virt-acpi-build.c` (1 617 lines, read 2026-10-23): `build_dbg2()` defined at line 945 and invoked at line 1407; `spcr_setup()`/`build_spcr(..., 2, ...)` lines 765-795, invoked under `if (ms->acpi_spcr_enabled)` at line 1402; `build_pptt()` invoked at line 1383; `build_gtdt()` defined at line 863 and invoked at line 1388; `#include "hw/acpi/wdat-gwdt.h"` line 68; `has_wdat = object_property_get_bool(wdt, "wdat", &error_abort)` line 1349, and `build_gtdt(tables_blob, tables->linker, vms, wdt && !has_wdat)` — i.e. WDAT and the GTDT watchdog entry are mutually exclusive. DBG2 reached QEMU for-6.2 via Eric Auger's series whose stated motivation was that Windows requires it; Ard Biesheuvel pushed back in review ("making things mandatory that aren't truly required from a functional perspective").

### [4] The newest Windows-motivated ACPI addition (WDAT watchdog for `arm/virt`) is upstream in master as a device option, and was justified explicitly by the absence of a Windows TCO watchdog driver.
- quote: "Windows doesn't ship built-in TCO watchdog driver, and users are forced to install vendor specific driver(s) if such exists. However OS provides a generic watchdog driver that uses ACPI WDAT table [1] to abstract actual hardware behind it. The same applies to ARM version of Windows."
- url: https://www.mail-archive.com/qemu-devel@nongnu.org/msg1170317.html
- source_type: primary
- published: 2026-02-06 (series by Igor Mammedov, quoted in Peter Maydell's reply of 2026-02-18)
- confidence: high
- detail: series `[PATCH 00/11] Introduce ACPI watchdog for Q35 and arm/virt boards` by Igor Mammedov (Red Hat) adds a WDAT table for the Q35 TCO watchdog and wires the SBSA GWDT into `arm/virt` with "necessary tweaks to GWDT to make usable with WDAT driver", CC'ing the SBSA people. Peter Maydell replied that `sbsa-ref` already has `sbsa-gwdt`. The feature is documented in current master: "`-device sbsa-gwdt,wdat=on` … The watchdog is described via the ACPI WDAT table (no FDT node), using a 1 kHz timer frequency." (https://www.qemu.org/docs/master/system/arm/virt.html). This is the model for how Windows-only ACPI needs get in: as an opt-in device property, not as a Windows machine type.

### [5] QEMU's arm `virt` DSDT already exposes a TPM 2.0 device using Microsoft's ACPI HID `MSFT0101` — the identifier Windows' TPM stack keys on.
- quote: "aml_append(dev, aml_name_decl("_HID", aml_string("MSFT0101")));"
- url: https://gitlab.com/api/v4/projects/11167699/repository/files/hw%2Farm%2Fvirt-acpi-build.c/raw?ref=master
- source_type: primary
- published: unknown (file read 2026-10-23)
- confidence: high
- detail: the device is `TPM0` with `_STR` = "TPM 2.0 Device", `_UID` = 1, `_STA` = 0xF, and a `_CRS` memory32 region derived from the sysbus TPM's MMIO plus an optional PPI region. Relevance to PocketVM: a `tpm-tis-device` + swtpm backend on `virt` presents itself to Windows as `MSFT0101`, so the "Windows 11 needs TPM 2.0" requirement is addressable in-tree; but the PPI region handling is still buggy (see finding 12).

### [6] Windows' graphics contract is the hard graphics constraint on `virt`: Windows requires a linear framebuffer via UEFI GOP and rejects `PixelBltOnly`, which is exactly what virtio-gpu's firmware driver provides — QEMU now documents this as a Windows incompatibility.
- quote: "On arm64, for non-Windows guests, `-device virtio-gpu-pci` provides additional functionality compared to `-device ramfb`, but is incompatible with Windows's UEFI GOP implementation, which expects a linear framebuffer to be available."
- url: https://www.qemu.org/docs/master/system/whpx.html
- source_type: primary
- published: unknown (QEMU master docs, 11.1.50)
- confidence: high
- detail: the same conclusion was reached in 2017 on the QEMU bug tracker with the Microsoft citation: "The virtio-gpu driver uses PixelBltOnly, which Windows explicitly doesn't support" (Googulator, 2017-11-14, https://bugs.launchpad.net/qemu/+bug/1717708). Laszlo Ersek's counter-proposal was to use VirtioGpuDxe's GOP only until `ExitBootServices()`, with a native ARM64 virtio-gpu driver injected afterwards; Gerd Hoffmann's `ramfb` (Nov 2017) was offered as the alternative and is what current guides (and QEMU's own WHPX example) use.

### [7] The first Windows-ARM64-under-QEMU thread was closed as "Invalid" in 2020 with no code change; the working configuration that emerged in 2017 is plain `-M virt` plus ARM64 builds of the virtio guest drivers.
- quote: "recent QEMU (2.11-rc1 and later) can run recent arm64 Windows images using -M virt and the virtio storage/input/networking drivers in the guest."
- url: https://bugs.launchpad.net/qemu/+bug/1717708
- source_type: primary
- published: 2017-09-16 (filed), 2017-11-18 (Baumann), 2020-08-12 (closed Invalid by Laszlo Ersek)
- confidence: high
- detail: "QEMU aarch64 can't run Windows ARM64 iso's" (oscarbg). Andrew Baumann's sample invocation: `-M virt -cpu cortex-a57 -m 4G -smp 4 -bios QEMU_EFI-arm64.fd -device VGA -device virtio-keyboard-pci -device virtio-mouse-pci -device virtio-net-pci -device virtio-blk-pci`, with `netkvm`, `vioinput`, `viostor` (virtio-win) rebuilt for ARM64. Shannon Zhao (Arm) stated the maintainer position: "I'm not sure what's the requirements for booting Windows on ARM64 virt machine since the OS is not open source. So it would be better someone from MS solves this problem or points what we missed for support Windows." No Windows-specific QEMU support was ever added as a result.

### [8] The same family of halt PocketVM sees was already reported in 2017: an "exception loop" that stopped newer Windows ARM64 builds even with a patched edk2, alongside device-specific boot blockers.
- quote: "This is able to boot the leaked Windows Server 2016 beta builds 14282, 14324 and 14877, but not 14901 or any of the Windows 10 Insider builds, due to an exception loop very similar to that seen when trying to run SBSA-ACS."
- url: https://bugs.launchpad.net/qemu/+bug/1717708
- source_type: primary
- published: 2017-11-14
- confidence: high
- detail: Googulator (community contributor; maintains a patched edk2 restoring features removed from mainline ArmVirtQemu because "they aren't compatible with KVM") also reported that in 2017 "the only storage option Windows can actually read and boot from is USB mass storage over EHCI — anything else is either lacking drivers (virtio-scsi and the various emulated LSI Logic adapters) or fails to start due to a resource conflict (AHCI, UAS, USB mass storage over XHCI)". This is the earliest located antecedent of a Windows-ARM64 early-boot self-halt on QEMU, and it was never root-caused in QEMU; the diagnosis stayed on the Windows/firmware side.

### [9] The only mature, actively maintained platform for Windows on QEMU arm64 is a downstream project, not QEMU itself: Open Device Partnership's `odp-platform-qemu-arm-virt`, which ships firmware, secure world, EC firmware, platform ACPI, a Windows image and end-to-end tests for `virt`.
- quote: "This repo contains all the necessary content for working on QEMU `virt` (arm64) platform"
- url: https://opendevicepartnership.github.io/odp-platform-qemu-arm-virt/print.html
- source_type: primary
- published: 2026 (docs build; repo last active 2026-08 per GitHub PR timestamps)
- confidence: high
- detail: Open Device Partnership (GitHub org `OpenDevicePartnership`, avatar id 173854189 — the Microsoft-initiated Linux Foundation project) assembles "the platform firmware, embedded controller firmware, secure services, UEFI, Windows image, and end-to-end tests". `mod/` holds "ACPI, UEFI, TF-A, Hafnium and secure service modules"; the Windows guest is Microsoft Validation OS (`postbuild/os/prebuilt/ValidationOS.vhdx`), not retail Windows 11. Boot paths: `make run` (UEFI only), `make run_os` (Windows), `make run_ec` (virtual RISC-V EC), `make e2e-test` (FF-A/FFA SMC tests over serial). Repo is small/low-profile: 71 commits, 1 star, 3 forks — maturity is "vendor reference platform", not community-maintained infrastructure.

### [10] ODP does not wait for QEMU upstream: it carries its own QEMU patch set (the only community Windows-on-arm64-QEMU patch queue found), applied to a pinned upstream tag and published as a Docker image.
- quote: "QEMU Builder has patches and HW features such as an I2C controller that we've added to QEMU."
- url: https://github.com/OpenDevicePartnership/odp-qemu-builder
- source_type: primary
- published: unknown (repos active through 2026)
- confidence: high
- detail: `odp-qemu-builder` builds from `QEMU_URL=https://gitlab.com/qemu-project/qemu.git`, default `QEMU_BRANCH=v10.0.0`, with "TPM support enabled", and applies exactly two files: `qemu-sbsa-patch.patch` (2 772 bytes) and `qemu-bus-emulation.patch` (90 242 bytes). Contents verified via the GitHub contents API: the sbsa patch adds `SBSA_TPM` at `0x60120000`, `SBSA_SECURE_UART_TEST` at `0x60130000`/IRQ 17 and a `create_tpm()` that binds `TYPE_TPM_TIS_SYSBUS` to the `tpm0` backend on `sbsa-ref`; the bus-emulation patch adds new files `hw/odp/{gpio.c,i2c-controller.c,i2c-target.c,pl061.c}` (373/661/486/463 lines), a new `hw/riscv/ec.c` RISC-V "ec" machine (243 lines), and edits `hw/arm/virt.c` plus `hw/arm/virt-acpi-build.c` (DSDT) and Kconfig/meson. `odp-platform-qemu-arm-virt` consumes it via a SHA-pinned builder image (`QEMU_BUILDER_IMAGE` digest, pinned in `.devcontainer/Dockerfile`) and its devcontainer cache lookup lists `ghcr.io/dymk/odp-platform-qemu-arm-virt-devcontainer` before the org cache, indicating `dymk` is the primary committer of the platform repo.

### [11] ODP's Windows-specific ACPI does not come from QEMU's ACPI generator at all — they inject compiled platform ACPI into a Windows disk image overlay, which is the cheapest way for a downstream project to change what Windows sees.
- quote: "Running `make run_os` downloads that ACPI-free base, compiles the current platform ACPI, injects it into a local qcow2 overlay, and boots the overlay."
- url: https://opendevicepartnership.github.io/odp-platform-qemu-arm-virt/print.html
- source_type: primary
- published: 2026
- confidence: high
- detail: the Windows image is produced by `.github/workflows/build-os.yml`, which downloads the latest Validation OS and injects drivers into a reusable base, then the platform ACPI is overlaid into a qcow2 copy. Debug tooling documented for the same path: WinDbg over `winbg -k com:ipport=56789,port=127.0.0.1`, `bcdedit /store BCD /set "{globalsettings}" bootdebug yes` for pre-NTOS failures ("If Windows doesn't boot properly on QEMU you are basically stuck wondering what is happening with no output after bootmgr starts"), and GDB against QEMU (`target extended-remote localhost:5555`) — i.e. the maintainers treat early-boot halts as normal and debug them, which is the workflow PocketVM would need to copy.

### [12] Windows-on-ARM as a QEMU *host* is now supported upstream (WHPX arm64 documented in master, minimum Windows 11 24H2 + Apr/May 2025 updates), with the Linux-side MSHV arm64 accelerator posted by Microsoft engineers in March 2026.
- quote: "On arm64, Windows 11 24H2 with the April 2025 optional updates or May 2025 security updates is the minimum required release."
- url: https://www.qemu.org/docs/master/system/whpx.html
- source_type: primary
- published: unknown (QEMU master docs, 11.1.50); WHPX doc patch landed via Paolo Bonzini's `[PULL 02/12]` of 2026-03-30
- confidence: high (docs) / medium (MSHV status)
- detail: the docs page documents `qemu-system-aarch64.exe -accel whpx -M virt -cpu host ...`, notes SVE/SME unsupported, and states the backend is "implemented on top of Vid, which is itself implemented on the same set of hypercalls as the `mshv` driver on Linux". The matching Linux series `[PATCH 00/14] Add ARM64 support for MSHV accelerator` by Anirudh Rayabharam (Microsoft) (qemu-devel, 2026-03-11, reviewed by Wei Liu / Alex Bennée / Mohamed Mediouni) is evidence that the same knowledge is landing symmetrically; I did not verify its merge state (no MSHV page exists in the 11.1.50 manual TOC).

### [13] Windows 11 ARM64 guests still have open, triaged upstream tracker items against `virt`'s PCIe and TPM paths as of October 2026 — the residual risk PocketVM would be inheriting.
- quote: "Windows 11 ARM64 guest livelocks in its PCIe root-port interrupt handler on pcie-root-port \"Command Completed\" (works with hotplug=off)"
- url: https://gitlab.com/qemu-project/qemu/-/work_items/4411
- source_type: primary
- published: 2026-09-04 (issue #4411); sibling issues #4663 2026-10-08, #4587 2026-09-25, #2893 2025-03-30
- confidence: high
- detail: from the QEMU GitLab tracker API (`projects/11167699/issues?search=Windows ARM64`, read 2026-10-23): #4411 open, labels `Device ➤ PCI`, `GuestOS ➤ Windows`, `Target ➤ ARM`, `Workflow::Triaged`; #4663 open, "tpm-tis-device aborts under HVF on Apple silicon (PPI region not page aligned); with ppi=off Windows 11 ARM64 rejects the TPM"; #4587 open, `hvf: abort() on HV_BAD_ARGUMENT when a guest RAM region is smaller than the host page size (regression in 11.0.0)`, `Device ➤ TPM`, `Workflow::Patch Available`; #2893 open, `Workflow::Needs Info`, "with m4 mac mini windows 11 arm 64 iso not booting for installation" (macOS/HVF host). Only four Windows-ARM64-specific guest issues exist in the whole tracker, none of them a fix for an early-kernel halt.

## Dead ends

- DuckDuckGo HTML and Lite endpoints: transport error / blocked; Bing returned region-stripped SERPs that ignored the query terms entirely (unusable for this angle).
- Mojeek, jsDelivr CDN, `raw.githubusercontent.com` (both `webfetch` and PowerShell TLS), `github.com/.../raw/...`: all unreachable from this environment.
- `lore.kernel.org` (Anubis proof-of-work) and `patchwork.ozlabs.org` (Anubis): cannot be read; `marc.info` failed DNS/SSRF checks; `mail-archive.com` was the working qemu-devel substitute.
- QEMU GitLab merge-request search API: HTTP 403 (auth required) — could not enumerate MRs for "Windows"/"WoA"; GitHub code search and the unauthenticated GitHub search API also hit rate limits.
- No upstream QEMU "windows" or "WoA" branch/tag was found anywhere (docs, tracker, mailing list); the phrase "Windows support" appears in QEMU only for the *host* (WHPX/WSL2 users) and in git tags of downstream mirrors.
- `odp-qemu-builder/qemu-bus-emulation.patch` was only inspected at file/hunk-header level (90 KB); the actual DSDT hunks in `hw/arm/virt-acpi-build.c` and the I2C/GPIO device models were not read line by line.
- No primary Microsoft document was found that states the Windows-ARM64 ACPI/UEFI contract beyond the GOP requirements page quoted second-hand in the 2017 bug (that document itself was not fetched).
