## E2 — 静态反汇编：main() 入口行为（新发现）

工具：`aarch64-linux-gnu-objdump`。init 入口 0x70000（bionic `_start`），GOT 槽 0x273510 的值是 `main` 地址 **0x76e74**（文件相对地址，即 load_bias + 0x76e74）。

`main()`（0x76e74 起）前几步，按顺序：

1. `setpriority(PRIO_PROCESS, 0, -20)`，返回值忽略。
2. `basename(argv[0])` 与 `"ueventd"` 比较——相等则跳 `ueventd_main`。
3. `argc >= 2` 时按 `argv[1]` 分派：`"subcontext"` → InitLogging 后调 0x774b4；`"selinux_setup"` → 0x102d58；`"second_stage"` → 0xc99a4（SecondStageMain）。
4. **`argc < 2`，或 `argv[1]` 不匹配上述任何一项时，落入 `LOG(FATAL) "Second-stage init requires an argument to main()"`**（字符串在文件偏移 0x28ffd，长 48 字节；`__FILE__` 为 `system/core/init/main.cpp`，行 85），随后经 `LogMessage` 析构 → abort。

即：**这个二进制的 main() 根本没有 first-stage 入口——它就是 second-stage init。** 无参数调用它时，它会主动 FATAL abort。这与观测到的 SIGABRT 完全吻合。

但有一个未解之处：FATAL 消息在任何一次既往日志里都没有出现过（`grep Second-stage` 在 smoke-serial.log、diag3-serial.log、diag5-serial.log 中均为 0 行），尽管 fd 2（串口）是通的（linker 警告能打印出来）。两种可能：(a) abort 实际发生在 `__libc_init` 调用 main 之前，main 的 FATAL 分支从未到达；(b) FATAL 消息被 libbase 默认 logger 吞掉。E3 用一次单变量实验区分。

附带证据：binary 内虽有 first-stage 相关字符串（`first_stage_device_initializer.cpp`、`/first_stage_ramdisk/fstab.`、`FIRST_STAGE_STARTED_AT` 等），但 main() 没有任何路径调用 FirstStageMain——first-stage 代码以库形式链接存在，却没有入口。

## 总根因链（E1 → 最终，2026-11-15 01:07–18:18 CST）

原始 SIGABRT（E1）并非单一原因，而是**四层缺失叠加**，逐层排除后才暴露下一层：

| 层 | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | init 无参 SIGABRT | GSI `/system/bin/init` 是 **second-stage-only**（main() 无 first-stage 入口；argc<2 → `LOG(FATAL) "Second-stage init requires an argument to main()"`，main.cpp:85） | 以 `init second_stage` 作为 PID 1 入口（wrapper exec） |
| 2 | `Could not read vendor SELinux version`（selinux.cpp:557） | 缺 `/vendor/etc/selinux/plat_sepolicy_vers.txt` | 补 `37.0` |
| 3 | `Failed to initialize property area`（property_service.cpp:1420） | **内核 `CONFIG_TMPFS_XATTR` 未开启** → tmpfs 上 `fsetxattr(security.selinux)` 全部失败（392 次，ENOTSUPP）→ `__system_property_area_init` 返回 -1 | 见层 3b |
| 3b | 同上（policy 已加载仍失败） | 同上；policy 加载不能修复 tmpfs 不支持 xattr 的问题 | **ext4 绕过**：将 128 MiB ext4 镜像作为第 4 块 virtio-blk 设备（vdd）挂到 `/dev/__properties__`（见 E27） |
| 4 | policy 加载 | GSI 只有 CIL 文本，无预编译 policy；系统 secilc 3.5 太旧 | 主线 secilc + libsepol 编译出 `sepolicy-main`（522,021 B，v33），`precompiled_sepolicy` + hash 文件，second_stage 的 `selinux_setup` 加载 |

另有两个独立的启动障碍（均在 property area 修复后暴露）：
- `/bootstrap-apex` 目录缺失 → `mount("tmpfs","/bootstrap-apex",...)` ENOENT → 补目录（E28）。
- `/dev/socket` 目录缺失 → property service socket bind ENOENT → wrapper 中 `mkdir -p /dev/socket`（E29）。

## E10–E16 — gdb 基础设施（01:29–01:45）
- `persp`（personality 包装器，NDK r27）使 init 基址确定性：0x5555554000；libc 基址每运行随机，需实时推导（init GOT 中 `__libc_init` 的 JUMP_SLOT，init+0x273a78，st_value 0x6f5f8；以 `abort` 交叉验证）。
- `libstop.so`（LD_PRELOAD 构造器）：SIGTSTP 停不住 PID 1；volatile `libstop_go` 自旋循环可用（仅当 `/proc/self/exe` == `/system/bin/init` 时构造器运行）。
- gdb 教训：必须选 userspace vCPU 线程；QEMU stub 不支持 `info sharedlibrary`/`info proc mappings`/`info auxv`（bionic linker 无 DT_DEBUG）；Python `read_memory` 失败但 CLI `x/` 可用。
- 回溯（首次）：`PropertyInit()+4124` → `SecondStageMain+556` → `__libc_init+120`。

## GDB 定量结论（01:45–02:00）
- `ContextsSerialized::Initialize` 返回 SUCCESS。
- 条件断点计数：open 0 失败，ftruncate 0，mmap 0，**`fsetxattr` 失败 392 次**（388 context 文件 + properties_serial + property_info + 余量）。
- `__system_property_area_init`（libc 0x93ee4）在 AreaInit 返回 true 但 out-flag 被置位时返回 -1；flag 仅在 fsetxattr 失败时置位（`csneg` 逻辑经反汇编验证）。
- 根因：**未加载 SELinux policy**（内核 "SELinux: Initializing." 但 init 报 "SELinux is disabled"），故 `security.selinux` xattr 设置失败。

## Policy 编译（01:50–02:00）
- GSI 只有 CIL 文本（`plat_sepolicy.cil` 3,418,955 B），无预编译二进制。
- 系统 secilc 3.5 太旧（拒 `nlmsg` permissionx、`netlink_xperm` policycap）。
- 修复：29 Oct 构建的主线 secilc + libsepol（`~/workspace/vendor-sepolicy/selinux-main/`，`LD_LIBRARY_PATH=.../libsepol/src` 运行），并删一行重复 `(typeattribute system_and_vendor_property_type)`（行 88748）。
- 产物：`/tmp/sepol/sepolicy-main`，522,021 B，SE Linux policy v33 MLS。Hash 文件：SHA256(plat_sepolicy.cil + mapping/202604.cil) = `f6d4906f…af7ba`。

## selinux_setup 路径（02:00–02:03）
- `init selinux_setup` 需 `/vendor/etc/selinux/precompiled_sepolicy` + hash 文件 `precompiled_sepolicy.plat_sepolicy_and_mapping.sha256`；缺失时回退到从 CIL 编译并因缺 `vendor_sepolicy.cil` 失败。
- 补齐后到 "Loading SELinux policy" 但 `Could not load policy: No such file or directory`——selinuxfs 未挂载。wrapper 中挂载 selinuxfs 后 policy 加载成功（capabilities 打印，file contexts 自 `/system/etc/selinux/plat_file_contexts` 加载），但 SELinux 变 ENFORCING（`enforcing=1`，audit 1404），init（domain `kernel`）被拒 `execute` linker64（label `rootfs`）：`execv("/system/bin/init") failed: Permission denied`。

## 手动 policy 加载（02:03–02:05，ramdisk m1-e22）
wrapper 挂载 selinuxfs，`cat precompiled_sepolicy > /sys/fs/selinux/load`，`echo 0 > /sys/fs/selinux/enforce`，再 exec `init second_stage`。Policy 加载、permissive 置位、`init second stage started!` 打印，但 PropertyInit 仍 FATAL；新行：`selinux: SELinux: Could not set context for /dev/__properties__/property_info: Operation not supported on transport endpoint`（ENOTSUPP）。

## 关键发现：CONFIG_TMPFS_XATTR 未开启（18:04）
内核配置 `~/workspace/kernel-android17-6.18/out/dist-qemu-virt/.config`：
```text
CONFIG_TMPFS=y
# CONFIG_TMPFS_POSIX_ACL is not set
# CONFIG_TMPFS_XATTR is not set        ← 根因
CONFIG_SECURITY_SELINUX=y
CONFIG_EXT4_FS=y
CONFIG_EXT4_FS_SECURITY=y               ← ext4 支持 security xattr
CONFIG_BLK_DEV_LOOP=y
```
tmpfs 完全不支持 xattr，故 `fsetxattr(security.selinux)` 在 tmpfs 文件上恒返回 EOPNOTSUPP。这是 property area FATAL 的真正根因，与 policy 是否加载无关。**正确修复是内核重编开启 `CONFIG_TMPFS_XATTR=y`**（Android 要求 tmpfs 支持 xattr；本次实验未重编内核，改用下面的 ext4 绕过）。

## E23–E26 — ext4 loop 挂载失败（18:05–18:11）
思路：把 128 MiB ext4 镜像（`mke2fs -t ext4`）loop 挂到 `/dev/__properties__`。三连失败：
- E23：toybox `mount -o loop` 需 exec 外部 `losetup`，ramdisk 无该命令（`/system/bin/losetup` 不存在）→ `mount: exec losetup: No such file or directory`。
- E24：补 `losetup`/`cat` → toybox 软链后，losetup 报 `/dev/loop0: No such device`；且 wrapper 用 toybox `cat` 写 `/sys/fs/selinux/load` 时分块写导致 policy 截断（`SELinux: ebitmap: truncated map` / `failed to load policy` / `cat: xwrite: Invalid argument`）——selinuxfs load 要求单次写完整个 policy；**结论：不要在 wrapper 里手动 cat policy，交给 second_stage 的 selinux_setup**（它用 libselinux 单次写）。
- E25/E26：losetup 要找 `/dev/block/loop0`（Android 约定，非 `/dev/loop0`）；补 `/dev/block/loop-control`、`loop0` 后仍 `Bad file descriptor`——initramfs（ramfs）上的文件作 loop 后端在该内核上失败。**loop 路线放弃。**

## E27 — ext4 直挂 vdd（18:12）✅ property area 通过

## E30–E31 — /system 挂载尝试（18:14–18:15，均失败，回归）
apexd 失败的原因：first-stage fstab 挂载从未执行（wrapper 绕过了 first-stage init，直接 exec second_stage），故 `/system` 从未挂载 vda；init 读到的 `/system/etc/init` 是 ramdisk 里复制的 .rc 文件，`/system/bin/apexd` 不在 ramdisk 中。
- E30：wrapper 中 `mount -t ext4 -o ro /dev/block/vda /system` 成功，但随后 `/system/bin/init: inaccessible or not found`。原因：GSI system.img 是 SAR 根文件系统，根下 `bin` → `/system/bin`、`init` → `/system/bin/init`、`etc` → `/system/etc` 均为**绝对路径软链**；挂到 `/system` 后自指成环（ELOOP）。SAR 镜像必须挂在 `/` 才能解析，挂 `/system` 是错的。
- E31：`mount vda /mnt/sys` + `mount --bind /mnt/sys/system /system` 成功（RC=0），但 init 立即 SIGSEGV（exitcode 0xb）——运行中的 init 依赖 ramdisk `/system` 下的 bootstrap linker/库，bind 换掉后 segfault。**此路不通，已回退。**

## E32 — apexd 依赖提取与回归（18:16–18:17）
- apexd 在 system.img 内：`/system/bin/apexd`（1,128,768 B，interp `/system/bin/bootstrap/linker64`）。经 debugfs 提取。
- apexd 的 NEEDED 中 ramdisk 缺 5 个：`apex_aidl_interface-cpp.so`、`libbinder.so`、`libvintf.so`、`libprotobuf-cpp-lite-7.36.2.so`、`libziparchive.so`；其传递依赖又缺 `libtinyxml2.so` 与 `libdl_android.so`。
- `libdl_android.so` 在 ramdisk 是指向 `/apex/com.android.runtime/lib64/bionic/libdl_android.so` 的软链（APEX 内文件）。从 `com.android.runtime.apex`（13,266,944 B，JAR）解出 `apex_payload.img`（ext2），再用 debugfs 取出真实 `libdl_android.so`（34,744 B，ELF）。
- 把 apexd + 7 个库拷入 ramdisk 后重建（m1-e32），结果**回归**：second_stage 启动后立即 SIGSEGV（exitcode 0xb），连 PropertyInit 都没到。
- 排查：重跑原始 m1-e29 文件也同样 SIGSEGV → **问题不在 ramdisk，在共享的 vdd（prop_area.img）**。该 ext4 镜像被多轮运行复用，残留的旧 property 文件导致 PropertyInit 时 init segfault。
- **修复：每次运行前重建 vdd**（`dd` + `mke2fs`）。重建后 m1-e29 恢复正常（见下）。

## 重要教训：vdd 必须每轮重建
ext4-on-vdd 绕过与 tmpfs 的关键区别：tmpfs 每次启动是空的，而 vdd 是持久磁盘，旧 property 文件会残留并导致下次启动 segfault。**每次 QEMU 运行前必须重建 `prop_area.img`**（或在 wrapper 中先清空）。这是该绕过的固有限制；根治仍是内核开启 `CONFIG_TMPFS_XATTR`。

1. **apexd / APEX bootstrap（当前终点）**：`/system/bin/apexd` 不在 ramdisk；补 apexd + 依赖库曾致 init segfault（原因未完全定位，疑似库版本/加载冲突），需单独攻关；另 `libdl_android.so` 来自压缩的 runtime APEX，APEX 挂载本身依赖 apexd，存在自举循环。建议：先在 ramdisk 外验证 apexd 依赖闭包（ldd 式检查），再决定是补库还是改走 first-stage fstab 挂载路线。
2. **根治 property area：内核重编开启 `CONFIG_TMPFS_XATTR=y`**，去掉 vdd 绕过与“每轮重建”的限制（tmpfs 天然每启动清空）。内核源码在 `~/workspace/kernel-android17-6.18`，需评估增量编译时间。
3. **真正的 first-stage init**：当前用 wrapper（sh 脚本）代 first-stage，跳过了 fstab first-stage 挂载（故 /system、/data、/metadata 未挂载）。要完整启动，需恢复 first-stage 流程（或让 wrapper 承担 first-stage 挂载——但 E30/E31 证明 SAR 镜像的挂载方式需谨慎设计，不能简单挂 `/system`）。
4. **静态 first-stage init 评估（任务书第 5 项）**：GSI init 本身是 second-stage-only，已证实；真正的 first-stage init 需从 AOSP 源码构建（`system/core/init` 的 first-stage 入口在 main() 的另一分支，GSI 二进制被裁剪/配置为 second-stage-only）。本实验未构建 AOSP；若走此路，需 AOSP 源码与构建环境，超出本次本地材料范围。
5. 不再做：loop 挂载（initramfs 文件作 loop 后端失败）、`/system` 直挂/bind（SAR 绝对软链/ELOOP、运行中换文件 segfault）、手动 cat policy 到 selinuxfs（分块写截断）。
