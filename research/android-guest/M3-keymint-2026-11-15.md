# M3 — Software KeyMint HAL（2026-11-15）

## 0. 任务与验收

- 唯一目标（P0）：为 PocketVM Android Guest 提供 Software KeyMint HAL，让 keystore2
  稳定运行、不再触发 fatal reboot。图形栈、post-fs-data 跟踪、Vendor fstab、VNDK、
  Zygote、PropertyInit 均不在本轮范围（P1–P6）。
- 验收：keystore2 稳定运行，不再触发 fatal reboot（串口日志为证）；同时记录
  post-fs-data 是否随之推进（只记录，不主动修）。
- 基线：M2 正式基线（`M2-vendor-apex-2026-11-15.md`，vendor-v3.img SHA 前 16 位
  `431cfa04eac710dd`，ramdisk `m1-p3.cpio.gz`，fstab `fstab.qemu.final`）。
  M2 终点：APEX bootstrap ✅ → servicemanager/vold/logd ✅ → post-fs-data 停滞
  （init.rc:681 之后）+ keystore2 反复 SIGABRT（5 次，~74s 触发 InitFatalReboot）。

## 1. 边界（用户已定，如实写清）

- Software KeyMint ≠ 完整 Android 安全硬件环境：只是 QEMU Guest 的软件实现，
  满足一部分 KeyMint 接口和系统服务依赖，不能等价于真实设备 TEE、硬件密钥隔离、
  StrongBox。密钥材料以 key blob 形式由 keystore2 持有（`/data/misc/keystore` DB），
  软件 keymaster 的密钥存储是纯内存（`PureSoftSecureKeyStorage` 只是内存 vector，
  无磁盘文件）；主密钥每启动随机生成，重启后旧 blob 不可解密（与模拟器行为一致；
  跨重启持久化是后续问题，不影响本次验收）。
- 研究 AOSP 的 Software KeyMint，**没有移植 Pixel 的 Tensor KeyMint**。
- Pixel 工厂镜像已从主开发路线退出；**本轮没有新增任何 Pixel 二进制依赖**
  （启动链里现有的 Pixel first-stage init 暂时保留不动）。

## 2. AOSP Software KeyMint 研究小结

### 2.1 keystore2 的发现机制（`system/security/keystore2/src/globals.rs`，上游 c652f6c 版全文 894 行）

- `keymint_service_name()`：TRUSTED_ENVIRONMENT 级 → VINTF 声明的实例 `default`
  （即 `android.hardware.security.keymint.IKeyMintDevice/default`）；STRONGBOX →
  `strongbox`；SOFTWARE 级直接返回 Err——**keystore2 从不直接要 SOFTWARE 级实例，
  软件 KeyMint 必须注册为 `default` 实例**。
- 无 `default` 声明时回落到 compat 服务 `android.security.compat`（本 GSI 无
  legacy Keymaster，也失败）。
- `connect_keymint()` 连接后调 `getHardwareInfo()`，按 `getInterfaceVersion()`
  （AIDL 版 ×100）决定是否包 BacklevelKeyMintWrapper（v1 才包；v2/v3 直接用）。
  GSI 版 keystore2 较新（含 module-hash 逻辑，KeyMint v4+ 特性）。
- keystore2 启动阻塞逻辑（已从 GSI 的 keystore2 二进制 strings 核实，
  `/tmp/m3/keystore2`，2,505,744 B，ELF aarch64，BuildID `10661bda…`）：
  启动时必须拿到 TEE 级（实例 `default`）KeyMint，并经
  `setAdditionalAttestationInfo` 发送 module info（module hash），成功后置属性
  `keystore.module_hash.sent=true`；任一失败即 panic（SIGABRT）。
  关键 strings：`Trying to find keymint for security level:`、
  `Trying to connect to genuine KeyMint service.`、
  `Trying to create V1 compatibility wrapper`、`Cannot connect to Keymint`、
  `No KeyMint instance found.`、`Terminating due to KeyMint not accepting module info, blocking boot:`、
  `Terminating due to failure to set keystore.module_hash.sent property, blocking boot:`、
  `Trying to construct mandatory security level TEE`。

  `libkeymaster_portable.so`、`libkeymaster_messages.so`、`libkeymint_support.so`、

### 2.3 AOSP 默认 KeyMint HAL 服务（`platform/hardware/interfaces/security/keymint/aidl/default/`，android17-release）

两种实现，本次选用 **C++ 版**：

1. **C++ 版** `android.hardware.security.keymint-service`（`service.cpp`，63 行）：
   `AndroidKeyMintDevice(SecurityLevel::SOFTWARE)` + AndroidSecureClock +
   AndroidSharedSecret + AndroidRemotelyProvisionedComponentDevice，全部实例
   `default`，NDK binder。rc：`service vendor.keymint-default
   /vendor/bin/hw/android.hardware.security.keymint-service`，class early_hal，
   user nobody。**只支持 KeyMint v4**（`system/keymaster/Android.bp` 明确注释；
   用 `keymint_cpp_impl_hal_aidl_ndk_shared` = keymint-V4-ndk）。✅ 本次选定。
2. **Rust 版** `android.hardware.security.keymint-service.nonsecure`（`main.rs`，
   110 行）：in-process 软件 TA（`kmr_ta_nonsecure::build_ta()`），注册 ALL_HALS
   为 `default`，用最新 AIDL；明确标注仅供测试/策略合规。未选用（Rust + kmr
   crates + AIDL Rust 绑定在 Soong 外构建过重）。
- VINTF fragment（`android.hardware.security.keymint-service.xml`）：keymint v5
  IKeyMintDevice/default + v3 IRemotelyProvisionedComponent/default。另有
  secureclock/sharedsecret fragment。`file_contexts`：nonsecure 二进制标
  `hal_keymint_default_exec`。
- **版本核定**：android17-release 分支 KeyMint AIDL 最新 v5（aidl_api 有 1–5 +
  current；current=v5）；GSI 有 V6-ndk 库（GSI 树比 android17-release 分支新），
  但兼容矩阵只认 1–5；IKeyMintDevice.aidl v4→v5 完全相同（v5 只在
  Algorithm/ErrorCode/KeyParameterValue/Tag 加 ML-DSA 相关枚举值 + 新文件
  MlDsaVariant.aidl），v3→v4 只加一个已废弃的 `setAdditionalAttestationInfo`
  方法。C++ 实现用 `KmVersion::KEYMINT_4`，`getHardwareInfo` 返回
  versionNumber=4、securityLevel=SOFTWARE、keyMintName=`FakeKeyMintDevice`、
  author=`Google`。**决定：按 v4 构建**（AOSP 对 C++ 实现的支持版本；
  module-hash 所需的 `setAdditionalAttestationInfo` 是 v4 方法；兼容矩阵 1–5
  覆盖 v4）。生成的 NDK 代码已确认 `IKeyMintDevice::version = 4`。
- `getRootOfTrust`/`getRootOfTrustChallenge`/`sendRootOfTrust` 在 C++ 实现里返回
  KM_ERROR_UNIMPLEMENTED（与模拟器行为一致，keystore2 对此只记日志、非致命）；
  `setAdditionalAttestationInfo` 透传给 AndroidKeymaster（已实现）；
  `addRngEntropy`、`deviceLocked`、`earlyBootEnded`、
  `convertStorageKeyToEphemeral` 均有实现。
- C++ 实现读属性（`system/keymaster/android_keymaster/keymaster_configuration.cpp`）：
  `ro.build.version.release`、`ro.build.version.security_patch`、
  `ro.vendor.build.security_patch`、`ro.boot.verifiedbootstate`、
  `ro.boot.vbmeta.device_state`、`ro.boot.vbmeta.digest`。其中
  `wait_and_get_property()` 会**一直等待属性出现**（每 15s 打一条日志）：
  `ro.vendor.build.security_patch` 目前 vendor/build.prop 里没有 → **必须在
  vendor/build.prop 里补 `ro.vendor.build.security_patch=2026-10-05`**
  （与 GSI 安全补丁一致），否则服务启动时挂住。`GetVbmetaDigest` 不等待
  （缺省全零），只打 `Unable to read vb_meta digest` 日志，非致命。
- Cuttlefish 另有 C++（PureSoftKeymasterContext，经 vsock/hvc 到 host secure_env）
  与 Rust 两套 KeyMint；Project Churro 的做法是从官方模拟器 vendor 镜像提取
  预编译 `android.hardware.security.keymint-service`——已记录为备用路线，未采用
  （优先源码构建）。

### 3.5 构建中遇到的三个关键问题（均已解决，有教训）

1. **NDK r27c 的 libbinder_ndk 太旧**：AIDL 生成的 NDK 代码用了更新的 API
   （`asBinderReference()` 未声明；`ICInterface::defineClass` 在 r27c 只有
   2 个参数而生成代码传 4 个）。解决：改用**平台版 libbinder_ndk 头文件**
   （frameworks/native，android17-release，与 aidl 同树），放在 include
   路径最前面以覆盖 NDK 的 `android/binder_*.h`。注意平台头文件分在三个目录：
   `libs/binder/ndk/include_cpp`（binder_interface_utils.h 等 C++ 头文件）、
   `include_ndk`（binder_ibinder.h 等 C 头文件）、`include_platform`
   （binder_ibinder_platform.h、binder_manager.h 等）。
2. **gen-build-list.py 的过滤 bug**：`if "test" in s` 把所有含 `attest` 的文件
   都滤掉了（AttestationKey.cpp、attestation_record.cpp、attestation_utils.cpp、
   soft_attestation_cert.cpp、soft_attestation_context.cpp，共 5 个），导致链接时
   `AttestationKey::writeToParcel/readFromParcel` 未定义。已修正为只滤
   `"/test"`、`_test.cpp`、`fuzz`；编译单元 96 → **101**。
3. **NDK libc++（`std::__ndk1`）与平台库（`std::__1`）ABI 不匹配**：
   用 NDK 头文件编译出的目标文件引用 `__ndk1::function/string/vector` 符号，
   而 GSI 的平台库（libbase、libcppbor、libbinder_ndk……）全部用 `__1` 编译，
   链接报大量 undefined symbol。解决：改用**平台版 libc++ 头文件**
   （platform/external/libcxx，`_LIBCPP_ABI_NAMESPACE` 默认 `__1`），并加
   `-nostdinc++`（否则 NDK 的 `c++/v1/stdint.h` 与平台 libcxx 的 `stdint.h`
   共用 `_LIBCPP_STDINT_H` 头文件保护宏，互相屏蔽导致 `int8_t` 等类型找不到），
   链接时用 `-nostdlib++ -lc++`（链接 GSI 的 libc++.so；GSI libc++.so 含
   libc++abi，导出 `__cxa_throw` 等，NEEDED 只有 libc/libm/libdl）。
   另：`libhardware/include/hardware/keymaster_defs.h` 是指向
   `include_all/` 的符号链接，sparse checkout 须同时检出 `include_all`；
   ng 代码 `#include <cppbor.h>`（无子目录），须加 `-Ilibcppbor/include/cppbor`。

## 4. SELinux 集成

### 4.1 GSI plat policy 现状（已核实，`/system/etc/selinux/plat_sepolicy.cil`，3,418,955 B）

- 有 `hal_keymint_service` 类型；`hal_keymint` 是 typeattribute，成员只有
  `hal_keymint_system`；`hal_keymint_server` 成员只有 `hal_keymint_system`；
  `hal_keymint_client` 成员：credstore、dumpstate、**keystore**、rkpdapp、
  system_server（keystore2 的 keystore 域已是 client，可 find 服务并 binder call）。
- **没有** `hal_keymint_default` / `hal_keymint_default_exec` 类型。
- `hal_keymint_system` / `hal_keymint_system_exec` 存在（Trusty/pVM 用的 system 侧
  keymint 域），**不适合**直接复用为软件 KeyMint 域。
- 属性规则已齐全（新域加入对应 attribute 即可继承）：
  `(allow hal_keymint_client hal_keymint_service (service_manager (find)))`、
  `(allow hal_keymint_server hal_keymint_service (service_manager (add find)))`、
  `(allow hal_keymint_server hal_remotelyprovisionedcomponent_service (service_manager (add find)))`、
  `(allow hal_keymint_client hal_keymint_server (binder (call transfer)))`、
  `(allow hal_keymint_server hal_keymint_client (binder (transfer)))`、
  `(allow hal_keymint_server servicemanager (binder (call transfer)))` + fd use。
- `plat_service_contexts` 已有映射：`IKeyMintDevice/default → hal_keymint_service`、
  `IRemotelyProvisionedComponent/default → hal_remotelyprovisionedcomponent_service`、
  `ISecureClock/default → hal_secureclock_service`、
  `ISharedSecret/default → hal_sharedsecret_service`。
- **plat policy 里没有任何关于 hal_secureclock_service / hal_sharedsecret_service /
  hal_frp_service 的 allow 规则**（类型存在，规则数为 0）。AOSP 的
  `hal_attribute_service()` 展开规则在 vendor .te 里，所以必须写进 vendor CIL。
- 通用 domain 规则已覆盖：properties_serial/properties_device、random_device
  （/dev/urandom 标为 random_device）、logd、system_linker_exec、binder_device
  （经 base_typeattr_408）。
- 属性读取：每属性另需 get_prop 式规则。服务需读的属性及其 context
  （plat_property_contexts，2043 行）：`ro.build.version.release`/
  `ro.build.version.security_patch` → build_prop；
  `ro.boot.verifiedbootstate` → bootloader_prop；
  `ro.vendor.build.security_patch` → vendor_security_patch_level_prop；
  `ro.boot.vbmeta.digest`/`device_state` 不在 contexts 里（GetVbmetaDigest 不等待，
  用全零缺省值，不阻塞）。
- plat_file_contexts：`/vendor/lib(64)?/` 无通用规则（只有 egl、vndk-sp、hw）；
  `/vendor/bin/hw` 无规则；无 keymint 相关规则；`/vendor/etc(/.*)? →

### 4.3 本次 vendor CIL（`~/workspace/vendor-sepolicy/vendor-sepolicy/vendor_sepolicy.cil`）

AOSP .te 翻译为 CIL，另加 AOSP .te 没有但本实现需要的两条 get_prop
（build_prop、bootloader_prop——C++ 实现读 ro.build.version.* 与
ro.boot.verifiedbootstate），以及 /vendor/lib64 闭包库的执行规则：

- 声明 `(type hal_keymint_default)`、`(type hal_keymint_default_exec)`；
  前者加入 domain、halserverdomain、hal_keymint、hal_keymint_server；
  后者加入 exec_type、file_type、vendor_file_type。
- init_daemon_domain 展开：init 对 _exec 的 getattr/open/read/execute/map、
  init→域 transition、域对 _exec 的 entrypoint/open/read/execute/getattr/map、
  init→域 siginh/rlimitinh、typetransition。
- hal_attribute_service 展开（secureclock、sharedsecret、frp 各两条：

## 8. 下一步建议

- **P1 post-fs-data**：本轮已证明 post-fs-data 不再停滞——P1 的“定位”工作
  事实上已完成（停滞的根因就是 KeyMint 缺失：keystore2 崩溃 → init 在
  post-fs-data 的 keymaster 步骤后无法继续；KeyMint 补上后全线通过）。
  建议 P1 改为“确认 post-fs-data 之后阶段无独立阻塞”，或直接并入 P4。
- **P4 Zygote/System Server**：直接阻塞是 surfaceflinger 反复 SIGABRT
  （无图形 HAL）。zygote 本身启动正常（4 次均成功 fork，socket 已建），
  问题在 surfaceflinger——与 P6 图形栈强耦合。建议 P4 与 P6 合并推进：
  先给 surfaceflinger 一个能跑的图形后端（virtio-gpu / 软件渲染），再看
  system_server。
- **P2 vendor fstab / P3 VNDK / P5 PropertyInit**：按原顺序继续；P5 的
  PropertyInit 定向验证（gdb/strace）仍欠，但本轮 property 等待
  （`apexd.status=activated` 709s、`keystore.module_hash.sent=true` 258ms、
  `ro.casefolding.adjusted=1` 201ms）均正常完成，PropertyInit 机制本身
  无异常表现。
- **V2 验证**：下一轮启动时用 `vendor-m3-v2.img` 代替 `vendor-m3.img`，
  确认 AVC 清零、其余行为不变。
- 备用路线（模拟器预编译服务 / Rust nonsecure 服务）：本轮源码构建已成功，
  不再需要。
